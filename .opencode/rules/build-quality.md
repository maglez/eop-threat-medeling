- Build MUST pass before any PR merge (`mvn verify` in CI)
- Code style enforced by `checkstyle` against the repo's own `checkstyle.xml` (4-space indent, 140-char line limit — NOT Google Java Style) — violations fail the build
- Static analysis via `spotbugs` — high/medium severity findings fail the build
- Code coverage via `jacoco` — minimum 80% instruction and 70% branch coverage, both evaluated over the whole bundle (`pom.xml:169`) with no exclusions and no per-class rule; the branch limit was restored by EOP-15 slice B once the domain had branches to measure — see ADR-006 as amended by ADR-031
- `maven-enforcer-plugin` enforces: JDK >= 21, dependency convergence (no version conflicts), no banned dependencies
- **Prose is a build gate too.** Documentation-integrity tests in `src/test/java/org/maglez/eop/docs/` run as part of the same `verify` phase and read repository files as text: `TrickPlayExceptionOriginTest` (EOP-14) pins an ADR-023 paragraph to the adapter, `AdrIndexConsistencyTest` (EOP-32) holds `docs/adr/README.md` against every ADR's status line, and `DeckArithmeticClaimsTest` (EOP-93) checks deck-arithmetic claims across **all** of `docs/**/*.md` and `src/**/*.java`. So editing a Markdown file anywhere under `docs/` can turn the build red. Two consequences worth internalising: their matchers are phrase lists rather than semantic analysis, so **a green build is not proof that documentation is correct** — it only proves the specific phrasings that have gone stale here before are absent; and if one of these guards ever becomes unfireable (invariant B is meaningless once no supported table size divides the deck evenly), **delete it rather than leave it passing**, per the branch-coverage lesson in ADR-006. See ADR-006 as amended 2026-08-18 (EOP-93)
- All new code must meet quality gates before CI passes
