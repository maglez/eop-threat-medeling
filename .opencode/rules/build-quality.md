- Build MUST pass before any PR merge (`mvn verify` in CI)
- Code style enforced by `checkstyle` against the repo's own `checkstyle.xml` (4-space indent, 140-char line limit — NOT Google Java Style) — violations fail the build. **Since EOP-120 it also enforces Javadoc *presence*, and that is now the bigger day-to-day constraint:** `MissingJavadocType` and `MissingJavadocMethod` at `scope=public` require a comment on every public type, method and constructor in `src/main/java`, and `JavadocMethod` requires every `@param` and every `@return` (`allowMissingParamTags` and `allowMissingReturnTag` are both `false`, and `minLineCount` is `-1` so a one-line public getter is not exempt). This is deliberately one half of a two-tool split and the half that is easiest to weaken by accident — do not relax `minLineCount` or any `allowMissing*` to silence a complaint about a getter. Changing them means amending ADR-006, because Checkstyle owning *missing* is what lets the Javadoc plugin run with `-missing` off
- Static analysis via `spotbugs` — high/medium severity findings fail the build
- Code coverage via `jacoco` — minimum 80% instruction and 70% branch coverage, both evaluated over the whole bundle (`pom.xml:169`) with no exclusions and no per-class rule; the branch limit was restored by EOP-15 slice B once the domain had branches to measure — see ADR-006 as amended by ADR-031
- `maven-enforcer-plugin` enforces: JDK >= 21, dependency convergence (no version conflicts), no banned dependencies
- **Javadoc is a build gate, and it is enforced by two tools rather than one.** `maven-javadoc-plugin` 3.11.2 runs `javadoc-no-fork` in the `verify` phase with `failOnError`, `failOnWarnings`, `show=public` and **`doclint=all,-missing`**, so a broken `{@link}`, a malformed tag or bad HTML in `src/main/java` fails the build. The `-missing` is load-bearing, not a shortcut: doclint's `missing` group ignores the `-public` flag and would demand a comment on every *private* field (~50 across the domain exception classes), and `doclint=all/protected` cannot be used at all — javadoc rejects access qualifiers on `-Xdoclint` outright. So the plugin owns **malformed** and Checkstyle owns **missing** (see the Checkstyle bullet above); never "simplify" this to `doclint=all`. The version is pinned exactly and is **not** covered by `tools/supply-chain/`, which audits the seven OpenCode npm plugins only — the whole Maven layer is uncovered, and this plugin is the fifth of five with identical exposure, so do not add it alone to that baseline. Three surprising directions. **A comment-only edit to a `.java` file can now turn `./mvnw verify` red**, which extends the blast radius of the prose gates below into source Javadoc. A warm `target/` may log `Skipping javadoc generation, everything is up to date.`, and the goal's mere presence in a log is **not** proof it re-analysed your edit — the staleness record holds 116 paths of which 93 are `.jar` and **zero** are `.java`, because the plugin's `StaleHelper.walk` uses a non-recursive `Files.newDirectoryStream`, so a Javadoc-only change need not invalidate it; CI is always the cold path (fresh runner, no `target/`) so every merge is gated on a full analysis, but locally run `./mvnw clean verify` before pushing if you only touched comments. And `debug=true` in the plugin configuration is **not** leftover scaffolding: without it the plugin deletes the `options` file its own staleness check stats, and a warm tree whose `target/maven-javadoc-plugin-stale-data.txt` is absent fails with `Unable to compute stale date: target/reports/apidocs/options` on a tree that is entirely correct — `clean` is the workaround, `debug=true` is the fix, and removing it reinstates the failure. See ADR-006 as amended 2026-08-20 (EOP-120)
- **Prose is a build gate too.** Documentation-integrity tests in `src/test/java/org/maglez/eop/docs/` run as part of the same `verify` phase and read repository files as text: `TrickPlayExceptionOriginTest` (EOP-14) pins an ADR-023 paragraph to the adapter, `AdrIndexConsistencyTest` (EOP-32) holds `docs/adr/README.md` against every ADR's status line, `DeckArithmeticClaimsTest` (EOP-93) checks deck-arithmetic claims across **all** of `docs/**/*.md` and `src/**/*.java`, and `EnumMirrorParityTest` (EOP-105) holds four mirrored enums (`PlayerRole`, `SessionStatus`, `ConnectionStatus`, `StrideCategory`) in three-way agreement across the Java enum, the `enum:` lists in `docs/api/openapi.yml` and the `as const` arrays in `ui/src/api.ts`, and `MermaidSequenceTextTest` (EOP-000) forbids `;` and `#` in every label of every Mermaid `sequenceDiagram` fence under `docs/**/*.md`. So editing a Markdown file anywhere under `docs/` can turn the build red — and so can editing `docs/api/openapi.yml` or `ui/src/api.ts`, which is the surprising direction: a front-end enum rename that passes `npm run verify` in `ui/` fails `./mvnw verify`. Three consequences worth internalising: their matchers are phrase lists rather than semantic analysis, so **a green build is not proof that documentation is correct** — it only proves the specific phrasings that have gone stale here before are absent; their *coverage* is likewise a hand-written list, so nothing detects a fifth mirrored enum added to `ui/src/api.ts` without a row in `EnumMirrorParityTest.mirrors()` — and that is not hypothetical, because `StrideCategory` was exactly such an unregistered mirror, found by a review agent rather than by the build, and registered only during EOP-105's own gate round; a further consequence of the same shape is that `typeScriptArrayValues` recognises only the `export const NAME = [...] as const;` idiom, so registering a mirror written as a bare union means rewriting the declaration first; and if one of these guards ever becomes unfireable (invariant B is meaningless once no supported table size divides the deck evenly), **delete it rather than leave it passing**, per the branch-coverage lesson in ADR-006. `MermaidSequenceTextTest` sits differently to the other four on the first of those consequences and squarely inside the third: it is structural rather than a phrase list, so it holds for diagrams nobody has written yet — but it proves only that two characters are absent, never that a diagram renders or says anything true, and its own coverage is the hand-written `MINIMUM_SEQUENCE_DIAGRAMS` floor that stops it silently matching nothing. See ADR-006 as amended 2026-08-18 (EOP-93), 2026-08-19 (EOP-105) and 2026-08-20 (EOP-000 and EOP-120)
