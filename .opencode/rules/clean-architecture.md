- Dependencies point inward: Entities → Use Cases → Interface Adapters → Frameworks & Drivers
- Cross-boundary data uses DTOs, not entities
- Core business logic has zero framework imports (no Spring, no Jakarta)
- Database and UI are details, not core architecture
- **The dependency rule binds Javadoc too, and there is exactly one way to satisfy it.** When an inner-layer type must *name* an outer-layer one in prose — an entity mentioning a repository port, say — write `{@code Type#member}`. Never `{@link Type#member}`, which needs an outward `import` to resolve, and never a fully-qualified `{@link org.maglez.eop.usecase.Type#member}`, which resolves without an import but emits a navigable outward reference in the generated docs and reads to the next author as licence for the real import. This is not stylistic: `pom.xml`'s Javadoc gate runs `doclint=all,-missing`, whose `reference` group **fails the build** on an unresolvable `{@link}`, so the tempting fix for that error is the import that violates the first bullet. The pattern to copy is `GameSession.java`'s `complete()` naming `{@code SessionRepository#recordCompleted}`, which explains itself in place. It is not the only such reference — `entity/` currently holds five, the most distant being `TrickAlreadyResolvedException` naming an adapter two layers out — so treat `complete()` as the worked example rather than assuming a second one would be novel.
