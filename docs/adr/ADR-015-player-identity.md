# ADR-015: Player Identity via a Server-Issued Opaque Token in Session Storage

**Status:** Accepted
**Date:** 2026-08-04
**Deciders:** @tech-lead, @security-auditor

## Context

The game has no accounts, no registration and no passwords, by design (PRD §4).
A player types a display name and joins with a session code. That is the whole
onboarding.

Anonymous is not the same as identity-free. The server must be able to answer two
questions on every request: *which player is this*, and *is it their turn*. Turn
order is derived by walking seat order, so "am I the active player" is a server
decision that the client cannot be trusted to assert. Without a credential,
anyone holding a session code could play a card as anyone else at the table.

The credential must survive two events. A browser refresh, because players will
refresh. And a **container restart**, because ADR-012 deploys by restarting the
container, so every deploy invalidates anything held only in server memory, and
the PRD makes resuming mid-trick a hard functional requirement.

There is one further constraint that turns out to be decisive, and it is not a
security constraint at all: **two players must be able to play from one browser**.
Not because real games work that way, but because local testing and a
single-machine demo both need it, and a mechanism that forbids it would be
discovered too late.

## Decision

**A server-issued opaque token, stored hashed in the database, held client-side in
`sessionStorage`, and sent in a custom request header.**

### The token

Generated by the server with `SecureRandom`, 256 bits, base64url-encoded. Issued
once when a player joins a session and returned in that response body — the only
time the plaintext ever leaves the server.

**Opaque and looked up, not signed.** A signed token (HMAC or JWT) would let the
server validate without a database read. Rejected: it requires a signing secret
as another environment variable to manage and rotate, and revocation becomes a
denylist — which is a database read, so the saving evaporates the moment
revocation matters. An opaque token is revoked by deleting a row. At 3–6 players
per session the lookup cost is not worth discussing.

**Stored SHA-256 hashed** in the `player` table, never in plaintext. This is a
bearer credential: whoever holds it *is* that player. Storing it in plaintext is
the same class of mistake as storing plaintext passwords, and the fact that the
stakes are lower does not make the reasoning different. A plain hash rather than
a password KDF is correct here precisely because the token is 256 bits of
`SecureRandom` output — there is no low-entropy secret to slow an attacker down
against.

**Persisted in PostgreSQL**, so it survives the container restart that every
deploy performs.

### Where the client keeps it

**`sessionStorage`, not a cookie and not `localStorage`.**

`sessionStorage` is scoped **per tab**. That single property resolves both
requirements at once: it survives a refresh, because a refresh keeps the same tab;
and two tabs are two independent players, because they do not share it. A cookie
or `localStorage` is scoped per origin and shared across every tab, which would
make two players in one browser impossible.

Two security properties come along for free. It is **not sent automatically**, so
CSRF is not a category of bug this application can have — there is nothing for a
cross-site request to ride on. And it is **not in the URL**, so it does not leak
through the referrer header, browser history, or a screen share of the address
bar during the very design review the game is played in.

### How it travels

A custom request header on every state-changing request. Custom rather than
`Authorization: Bearer` because this is not OAuth and naming it so would invite
the assumption that it behaves like one.

The SSE stream is a plain `GET` and takes the same credential. Note that the
browser's `EventSource` API cannot set custom headers, so the streaming endpoint
will need either `fetch`-based streaming or the token as a query parameter —
and if it becomes a query parameter, it lands in server access logs, which
undoes one of the properties above. **This is an open implementation question for
EOP-10, and the answer must not be "query parameter" by default.**

## Consequences

**Positive:** no dependency, no signing secret, no session store. Revocation is
`DELETE`. The threat model is small enough to hold in one's head, which for a
control this load-bearing is worth more than sophistication.

**Positive:** two players from one browser works, so a local demo and an
integration test can both exercise a real multiplayer session without two
machines.

**Negative — this token is the entire control.** There is no password, no second
factor and no rate limit on anything except joining. Defence in depth is a stated
project rule (`.opencode/rules/security.md`) and this decision does not satisfy
it; it is a single gate. That is accepted for a PoC with no real data, and it is
recorded here so nobody later mistakes it for a layered design.

**Negative — the token is sniffable on the wire.** ADR-012 accepts bare-IP HTTP
with no TLS. Anyone on the network path between a player and the instance can
read the header and impersonate that player for the rest of the session. This is
not a flaw in the token design; **no credential design survives a plaintext
transport.** It is acceptable for a demo where the worst outcome is a stranger
playing a card in a threat-modelling game. It is unacceptable for anything real,
and the fix is TLS, not a cleverer token. If this application ever holds
something worth taking, TLS comes before the next feature.

**Negative — closing the tab loses the credential.** `sessionStorage` does not
survive tab close, so the player must rejoin. Refresh is safe; close is not. This
is the direct cost of the per-tab scoping that made two-players-one-browser
possible, and it is the right trade for a session lasting 60–90 minutes.

**Negative — display names are unverified.** Nothing stops two players choosing
the same name, or one choosing a name that impersonates another. The token
distinguishes them to the server; the humans on the call distinguish them to each
other. Names must still be length-bounded and escaped on output, because
"anonymous" does not mean "unvalidated".

**Neutral — no cross-session identity.** A player who joins two games is two
unrelated players. Consistent with the PRD's exclusion of cross-session history.
