## [1.0.0-SNAPSHOT] — Unreleased

### Added

Working code and tooling that exists in the repository today.

- Walking Skeleton: Spring Boot 4.1.0 + Java 21 + `GET /health` (ADR-002)
- Continuous integration: GitHub Actions running `./mvnw verify` on push and PR, uploading the built artifact, then building the container image, smoke testing it against a real PostgreSQL and publishing it to GHCR on `main`
- Front end: React + TypeScript + Vite under `ui/` with GOV.UK Design System CSS (ADR-009). One page — the application shell plus the card catalogue fetched live from the API. Both calls to action are visibly disabled, because a button that looks live and does nothing is worse than one that admits it
- Single-origin serving: Caddy serves the built front end and reverse-proxies `/api/*` and `/health` to the application on the same origin (ADR-017). The application container publishes no host port at all, so there is no cross-origin request anywhere and therefore no CORS configuration to maintain
- Front-end quality gates: a dedicated `ui` CI job runs type checking, linting, unit tests and the production build as four separate steps. It is deliberately separate from the Java `build` job — the single required status check protecting `main` stays Java-only and fast, and a front-end failure reports as a front-end failure
- Container images: multi-stage `Dockerfile` producing a non-root JRE image and `ui/Dockerfile` producing a Caddy image carrying the built front end, `compose.app.yml` running both alongside containerised PostgreSQL, published to `ghcr.io` by CI with no repository secrets (ADR-012, ADR-017)
- Deployment infrastructure: Terraform under `infra/` describing a single `t3.small` EC2 instance in a dedicated VPC with an Elastic IP and a separate encrypted EBS data volume (ADR-012). Validated with `terraform validate`; no `apply` has run yet because no AWS account has been provisioned, and cloud deployment is deferred in favour of running locally (see the ADR-012 amendment)
- Local container runtime: Colima provides a Docker-compatible daemon from Homebrew formulae with no administrator rights (ADR-016). The whole stack — application and PostgreSQL — now runs on a developer machine with the same `docker compose -f compose.app.yml up -d` that CI and the EC2 bootstrap script use
- Build quality gates: Checkstyle (`checkstyle.xml`), SpotBugs, JaCoCo 80% instruction coverage, Enforcer (ADR-006)
- Database migrations: Liquibase with a master XML changelog, H2 in the default profile, PostgreSQL in `prod` (ADR-008). The first migration creates the `card` table; the second replaces the placeholder deck with the real one
- Card catalogue: `GET /api/v1/cards` and `GET /api/v1/cards/{cardId}` serve the deck as read-only reference data (EOP-6)
- The real Elevation of Privilege deck: all 78 cards, thirteen ranks in each of the six STRIDE suits, transcribed from Microsoft's published deck and seeded by an additive data-only migration (EOP-13). © 2009 Microsoft Corporation, licensed CC-BY-3.0 US — attribution is the only obligation the licence imposes and it is discharged in the running application, not merely in the repository. The printed deck held 74 because two suits started above the two; the published machine-readable file completes them to thirteen apiece, which also removes two suit-specific special cases from the trick rules still to be written
- Trick-taking rules as pure domain types: `Hand`, `Hands`, `Trick` and `TrickPlay` under `org.maglez.eop.entity`, with zero framework imports, carrying the whole rule set the game turns on — dealing, following suit, turn order, and who takes the trick (EOP-14, ADR-023). Four decisions are worth naming. **The opening lead is derived, never written down:** the seat holding the lowest-ranked Tampering card *actually dealt* leads, because the printed 74-card deck starts on the three and the seeded 78-card deck on the two, and both are right for their own deck — a literal `2` or `3` anywhere in this code would be a defect against one of them, so `Hands.openingLeaderSeat()` computes it and `NoTamperingCardDealtException` covers the one case the rule cannot answer rather than falling back to an arbitrary leader. **Every card is dealt**, with the remainder going to the lowest seats, so at four and five players hands are unequal and the final trick is short; setting the remainder aside instead would have been tidier but can orphan the card the opening-lead rule needs, turning a derived rule into a hidden fallback reached only at certain player counts. That in turn makes a trick *one card from each seat that still holds cards* rather than a fixed count, so turn order is "the next seat clockwise still holding a card" and not the leader's seat plus the number of cards played — the simpler formula is correct for every trick except the last one at four and five players, which is why ADR-019 now carries a dated amendment where an implementer would otherwise copy it. **A card played with no threat linked is a legal, ordinary play:** it still competes for the trick and simply scores nothing, so `TrickPlay.threatLinked` is a fact about a play and not an error, and a linked threat naming no component is accepted too — a facilitation tool that refuses a play in a live session because a text box is empty gets in the way of the conversation it exists to support. **A card named in a request is resolved out of the hand before any rule is applied to it,** and there is one guarded way in: `Trick.acceptPlay` checks the turn, resolves the card, checks follow-suit against the *resolved* suit and appends the play, with `Trick.play` reduced to package-private so nothing outside the domain can reach the unguarded mutator. A card is named by identifier, so its suit and rank travel as the caller's *claim*; checking possession by identifier and then reading the suit off the submitted object let a holder of the two of Tampering submit that identifier labelled ace of Elevation of Privilege, pass possession, escape follow-suit because the claimed suit was trump, and take the trick with a card that was never dealt. Three public checks a caller was merely *documented* to call in the right order were two optional guards in front of an open mutator, not defence in depth. **The acting seat is a parameter in its own right and is never read from the payload:** `acceptPlay(int actingSeat, TrickPlay candidate, Hands hands)` takes the seat the caller has authenticated, refuses the play with `NotYourSeatException` if it describes a different seat, and then *derives* both the hand and the set of seats still holding cards from `hands` rather than accepting either. An earlier revision took the seat from the submitted play and cross-checked only the hand against the player, which is a two-way check on a three-way fact — seat, hand and player — and `Hand` deliberately carries no seat number, so the binding could not be made from those arguments at all. Because the session state already publishes every player's identifier *and* seat to every other player, a player really sitting at seat 2 could submit its own identifier with someone else's seat number and its own hand: the play was accepted out of turn, the victim's seat was marked as having played so they were locked out of the trick for good, and the attacker could then play a second card from the same hand at its real seat and take the trick. The player identifier remains the one caller-supplied claim, and it is checked against the seat's occupant rather than believed. **The seat is settled before anything else is looked at** — whether it is a seat at this table at all, whether the play claims that seat, and whether the player the play names is the one occupying it — because all three are answered entirely from facts the requester already sent, so a refusal discloses nothing it did not already know. A play naming a seat's non-occupant is refused with `PlayerMismatchException`, its own type rather than a bare `IllegalArgumentException`, so the boundary can tell impersonation from a malformed argument without matching on message text and can carry both player identifiers as fields instead of interpolating them into a message a caller reads. Turn order comes next, before the card is looked at, so a player who is not to play learns nothing about their own cards from the refusal, and `Trick.nextLeaderSeat(seatsHoldingCards)` passes the lead on when the winner has run out of cards — a winner's seat handed back unconditionally would open a trick nobody could play into, which is reachable at four and five players and would have stopped the game with no exception to log. Free text a player types is bounded and refused if it carries control characters or bidirectional overrides, because a NUL byte cannot be stored in a PostgreSQL `text` column, CR and LF in text that reaches a log let a player forge log lines, and a bidi override lets a component name display differently from the one stored. On rendering: `Hand`, `Hands` and `TrickPlay` print only counts, because knowing an opponent's cards is knowing what they can and cannot follow with, and the default rendering would leak a hand — or a player's notes — into any log line that interpolated it. `Card.toString` drops its threat prompt as bulk rather than as a secret; the deck is published, so what is confidential is the *association* between a player and an unplayed card, and that guarantee lives in the redacted containers and in `Hand.cards()` being documented as confidential rather than in `Card` itself. A `Trick` also refuses, at construction, a play list in which one player holds two seats or two plays share an identifier, and refuses plays that do not run clockwise from the leading seat — the first of those is the stored form of the seat-impersonation defect above, and all three are checks a trick can make from the plays alone. What it cannot check is follow-suit, because that is a question about a hand and a trick holds no hands, so `Trick.reconstitute` is documented as **not** a validating gate for the rules of play and Slice B's persistence adapter must be trusted to store only what `acceptPlay` produced. `Hands.deal` refuses two seat assignments sharing a seat order, which previously collapsed silently on insertion and left one seat holding two round-robin shares of the deck. `docs/requirements/PRD-eop-card-game.md` §3.3 now carries dated deviation notes against the two sentences the implemented rules depart from — "one time around the table" and "the winner of a trick leads the next trick" — each linking ADR-023, because both are the shipped instruction card's wording and both are right for a game in which every hand empties together. All six of the story's domain refusals are now mapped to problem details and unit-tested, as the error-handling rules require of every known exception: a play claiming a seat its requester does not occupy and a play naming a player who does not hold that seat are both **403**, being impersonation rather than malformed input; a play out of turn is **409**; a play that breaks follow-suit, or names a card the hand does not hold, is **422**, because every field parsed and the refusal came from a rule of the game. Two of those mappings deliberately do not echo the exception's message: the card refusal reports only the card identifier and not the identifier of the hand, and the player-mismatch refusal returns a fixed sentence, its message having been reduced to name a seat and nothing else so that logging it cannot leak either player. A deck with no Tampering card is the one **500** here, because the deck is seeded reference data and every valid deck contains the suit. Nothing is wired up yet — no schema, no endpoint, no dealing on session start — and scoring is EOP-15
- Storage for the trick-taking domain: migration `004-trick-play-schema.xml` creates `hand`, `hand_card`, `trick`, `trick_play` and `trick_play_component`, and adds `game_session.current_leader_seat` (EOP-14, ADR-023). It also adds `uq_player_id_seat` to `player`, a table it does not create. The schema lands before the JPA entities and adapters deliberately, because `ddl-auto: validate` fails startup on an entity with no matching table. Six decisions are worth naming. **`trick_play.components` becomes a child table with an explicit `ordinal`, and the 20-element cap is enforced three times over** — once in the domain constructor, once in storage as `PRIMARY KEY (trick_play_id, ordinal)` plus `CHECK (ordinal >= 0 AND ordinal <= 19)`, and once at the boundary in the slice that adds the request DTO. That is defence in depth rather than duplication: the domain stops bad input, the constraints stop a bad write from a future adapter bug or a hand-run statement. `(trick_play_id, component_name)` is deliberately *not* unique, because the domain accepts repeated component names and a stricter constraint would turn a legal play into a 500. **`hand_card` gets no ordinal**, which looks inconsistent next to the components table until you notice that `Hand` sorts its cards in its own constructor so that two hands holding the same cards compare equal whichever order they arrived in — dealing order carries no meaning, whereas the order a facilitator typed their component names in does, so one is canonicalised and the other preserved as typed. **`trick` gets no `led_suit` column**, because `Trick.ledSuit()` derives it from the first play and a stored copy would be a second authority no write path populates. **The three `trick_play` unique constraints carry the invariants through a reload**, so they survive rather than living only in whichever entity happened to be in memory — but only one of them is the stored form of a Slice A security defect. `(trick_id, card_id)` closes card forgery within a trick. `(trick_id, player_id)` stops one player occupying two seats in a trick, which is a *different* exploit from the seat impersonation Slice A had to fix twice, and an earlier draft of this entry claimed otherwise. **Seat impersonation is closed instead by binding a stored seat to the seat its player actually holds:** `uq_player_id_seat` on `player (id, seat_order)` gives a composite foreign key something to reference, and `fk_hand_player_seat` and `fk_trick_play_player_seat` then make a hand or a play at a seat its player does not hold structurally unrepresentable, rather than merely unlikely. That reverses a deferral taken earlier the same day: the seat and cross-session protections were argued as one problem and a sound objection to the expensive half — denormalising `game_session_id`, a copy that can disagree with its parent — was allowed to carry the cheap half with it, when in fact `seat_order` was already on both tables and the binding needed one unique constraint that adds no invariant of its own. The single-column keys to `player(id)` are subsumed by the composite ones rather than omitted, and that subsumption holds only while both key columns stay `NOT NULL`. **What is deliberately still not enforced is session scoping**, and the honest consequence is that the composite key proves a player holds that seat *somewhere*, not that they are at this trick's table — seats are numbered from zero in every session, so a player at seat 2 in another session still satisfies it and can still take this session's seat-2 occupant out of play. Narrowed to cross-session attackers, then, not closed; it is owned by Slice C's play use case, which resolves the acting player from the identity token, and ADR-023 records both the reversal and what remains. **Foreign keys were missing on `trick_play.card_id` and `trick.winner_play_id`** and are now present; an unconstrained `card_id` in particular left card forgery re-openable one layer below the code that had just been hardened against it. `fk_trick_winner_play` is `ON DELETE SET NULL` rather than the `NO ACTION` first written, because measurement showed NO ACTION made a resolved trick undeletable outright — at the cost that deleting a winning play directly now silently unresolves its trick, which nothing but a comment currently prevents a later slice from doing. The concurrency test ADR-023 places in this slice rather than a later one — before the constraint exists there is nothing to assert against — drives one player racing itself through separate JDBC connections, which is the ordinary double-tap a real client produces; a second, sequential test uses two players from different sessions who both legitimately hold the same seat number, because that is the only construction left in which `uq_trick_play_trick_seat` is the sole constraint that can fire, and it doubles as the recorded proof of the cross-session gap above
- Range bounds on every seat and sequence column: migration `005-seat-and-sequence-bounds.xml` adds `chk_player_seat_order`, `chk_trick_sequence` and `chk_game_session_current_leader_seat` (EOP-14, ADR-023). This closes a gap found by measurement rather than by reading: against the merged Slice B schema, `player.seat_order = -7`, `trick.sequence = -5` and `game_session.current_leader_seat = 9999` were all *accepted* by the engine, while the domain refuses all three. Three points are worth naming. **One CHECK on `player.seat_order` bounds three tables**, because `fk_hand_player_seat` and `fk_trick_play_player_seat` bind `hand` and `trick_play` to `player (id, seat_order)` — so the seat range on the child tables is inherited, and the composite keys that carry it prove consistency with the parent but never validity, which is exactly why the parent needed a bound of its own. **`trick.sequence` gets a lower bound only**, because no upper bound is derivable — a three-player deal runs to 26 tricks and no domain constant caps it — so `>= 1` is the whole of what is known and inventing a ceiling would reject legal play. **The bounds are pinned to `GameSession.MAXIMUM_PLAYERS` by a test that reads the changeset XML**, since Liquibase cannot read a Java constant and the literal `5` is a hand-copied counterpart: raising the player cap without editing the migration would leave storage stricter than the domain and turn a legal join into a 500. Each constraint is tested in both directions, because a test that only proves rejection would pass just as well against a CHECK that rejected every value, legal ones included. Adding a constraint to `player` from a later changelog file rather than editing `003` is the only lawful option — merged changesets are immutable (ADR-008) — and follows the precedent `004` set when it added `uq_player_id_seat` to the same table. Writing all three as raw `<sql>` is likewise forced: `addCheckConstraint` is a Liquibase Pro change type and is absent from the open-source `liquibase-core` this project depends on. Landing `005` also exposed a latent defect in Slice B's own round-trip test, which rolled back a hard-coded nine changesets to undo `004` — correct only while `004` was the last changelog file, since Liquibase counts backwards from the last change *applied*. It now derives the count from `DATABASECHANGELOG`, so `006` cannot re-break it
- An error vocabulary for trick play: seven domain exception types and their problem-detail mappings — `PlayerNotInSessionException` (404), `HandAlreadyDealtException`, `HandNotDealtException`, `TrickAlreadyOpenException`, `AlreadyPlayedInTrickException` and `CardAlreadyPlayedException` (409), and `WinningPlayNotInTrickException` (422) — landing ahead of the use cases that will throw them (EOP-14, ADR-023). Five decisions are worth naming. **A caller who is not in the session is answered exactly as a session that does not exist**, byte for byte and not merely with the same status: a 403 would confirm to a stranger holding a guessed or leaked identifier that it guessed correctly, and two 404s with different titles would be as good an oracle as a 403, so the test asserts equality of the two whole `ProblemDetail` bodies. The parity is held in place by the exception itself, which builds the same message as `SessionNotFoundException` for the same identifier and carries the session id **and nothing else** — a field naming the player, the seat or the reason would eventually be logged into a response, and a field that does not exist cannot be. This follows the fixed-body reasoning already written for an unknown join code, with the one deliberate difference that a join code is blanked because roughly thirty bits are guessable while a caller-supplied session identifier can be echoed back safely. **The candour argument that licenses naming a missing session is now scoped in the code that makes it**: the Javadoc on `SessionNotFoundException` and its handler argued from a 122-bit identifier, which is sound about whether a session exists and says nothing about who may see it, so both now cross-reference the membership answer rather than leaving the next reader to generalise a correct argument past its premise. **A winner from another trick is 422 and not 409**, because a conflict entitles the caller to retry once the state moves on and no state this application can reach makes a play from one trick the winner of another; it is also logged at warning level with both identifiers and returns neither, since ADR-023 records that this check will never have a storage constraint behind it — the composite key that would provide one collides with the rule that lets a winning play be deleted — so the log line is the only evidence that will ever exist. **The two conflicts on a trick are kept apart**: one refuses a second play from a seat, the other one card appearing twice whichever seat played it, and a test pins the titles as unequal so that collapsing them into a single "conflict" cannot pass. **The two states of the deal are kept apart on the same reasoning, and naming the second of them is what took a seventh type**: `HandNotDealtException` is the mirror of `HandAlreadyDealtException`, the two being opposite states of one column — `game_session.current_leader_seat` — and a vocabulary naming only one of them forces the other to be reported as something it is not. Before it existed, that branch of `TrickPlayRepositoryAdapter.sessionMoved` answered `SessionNotJoinableException` carrying `IN_PROGRESS`: the right status with an explanation that contradicted itself, telling a caller a session was not joinable while handing back the status saying it was in progress. @architecture-guardian found it in this slice's architecture review, and the fix was a type that can name the state rather than a different status code — the branch is reached by asking to open the first trick before the deal, which is an ordinary caller mistake rather than a broken invariant, hence a 409 and not a 500. The two 409 titles are deliberately unequal, and a test pins that they do not collapse into each other, because both are conflicts on one column and the title is the only thing saying which way it went. The translation table in ADR-023 was also one row short and is amended here: `uq_trick_session_sequence` is reachable by two requests racing to open the same trick, and without a name for it that race answered 500. What C1 cannot yet test is the status over the wire, because it adds no route — the handlers are proved as pure functions here, exactly as the existing mappings are, and the wire-level assertions arrive with the endpoints
- Persistence mappings for the trick-play tables: JPA entities for `hand`, `hand_card`, `trick`, `trick_play` and `trick_play_component`, plus the `current_leader_seat` column on the session entity (EOP-14, ADR-023). The point of the commit is not the eight new classes but what mapping them switches on. `spring.jpa.hibernate.ddl-auto` is `validate`, and until now that setting was nearly free: three tables were mapped, the five created by Slice B were not, and Hibernate validated nothing about them — so a mapping could disagree with the migrations indefinitely and only a query that happened to touch the wrong column would ever say so. Mapping them means every column and type on all eight tables is now checked at every context start, on H2 in the suite and on PostgreSQL in production. Because that check is silent when it passes, it gets a test of its own rather than being left as something the other integration tests catch by accident: `MappedSchemaValidationIntegrationTest` asserts the effective `ddl-auto` value, so switching it to `none` fails loudly instead of quietly removing a guard, and then issues a real bounded `SELECT` of every mapped column of every entity, which is a stronger check than startup validation and one that names the entity when it breaks. The test was confirmed non-vacuous by measurement — renaming a single mapped column to `seat_ordering` turned all nine cases red — because a schema test that cannot fail is worse than none. Three mapping decisions carry reasoning. **No collection mappings anywhere**, following the session entity's existing refusal of `@OneToMany`: a played card is one delete and a play is one insert, and a cascade or orphan-removal mapping would turn each into a diff of two collections, which matters here more than it did for seats because the statement issued has to be exactly the statement it looks like — the row lock taken before it is the concurrency guard. **The two link tables use `@IdClass` rather than `@EmbeddedId`**, since both have a composite primary key that genuinely is their identity and no surrogate to invent; `@IdClass` keeps the key columns as ordinary fields, so a query reads `deleteByHandIdAndCardId` instead of routing every predicate through an embedded object. **`current_leader_seat` is mapped on the row and deliberately nowhere else** — the domain `GameSession` gains nothing, because the current leader is a fact about the trick in progress and `Trick` already derives whose turn it is from its own plays, so a copy on the aggregate would be a second authority on it. It is stored because it is the compare-and-set witness the conditional writes name, it is `Integer` rather than `int` because null is meaningful and is how "no cards dealt yet" is stored, and it advances once per trick rather than once per play. A play reads it and takes the row lock without changing it
- Storage for dealt hands and played tricks: the `HandRepository` and `TrickRepository` ports, five Spring Data interfaces, one `TrickPlayRepositoryAdapter` implementing both, and three further conditional updates on the session row — `claimDeal`, `touchWhileLeaderSeatIs` and `advanceLeaderSeat` (EOP-14, ADR-020, ADR-023, ADR-024). Five decisions carry the design and govern the first half of this entry; what follows them records what shipped, and the argument that used to fill the rest now lives in an ADR of its own. **There is no `save`**: each write is narrow and conditional on the state the caller observed, because a blanket save would have to diff an immutable aggregate against storage to learn which rows to write and could not be conditional on anything — which is precisely the compare-and-set turn order depends on. **Both ports are implemented by one class**, because playing a card deletes a `hand_card` row and inserts a play and its components and those must commit together; the two decompositions that keep one adapter per port either admit that torn state or put `@Transactional` in the use-case package. *(Retracted — see ADR-024's amendment and the next entry: those are not the only two decompositions. A `@Transactional` method in the outer ring composes two adapters through the `REQUIRED` propagation they already carry, with no import inside `usecase`. One class per aggregate survives on ownership grounds, not on a false dichotomy.)* **Every write begins with a conditional update on the session row**, which is both the compare-and-set whose zero-rows answer means the world moved and the row lock taken in the order the ADR requires (session, then hands, then tricks). Zero rows is never success and never a server fault: one helper spends a single extra read on the already-failing path to answer that the session is missing, is not in progress, has already been dealt, has not been dealt at all, or that the caller's leader-seat snapshot is stale — the last being an out-of-turn play, since the leader seat is the value turn order is computed from, and a double resolution lands there too because the first resolution moved the seat. **Hands are read whole or not at all**, since `Hands.reconstitute` re-runs a cross-seat invariant no database constraint stands behind and a per-seat read would satisfy it vacuously, switching off its only enforcement; writes stay a one-seat delta. Plays are ordered by rotation from the trick's leader seat rather than by `played_at`, because the domain reads the led suit from the first play and a timestamp can tie. **The seat foreign keys are a backstop rather than the check**: the adapter reads the session's seats before inserting and refuses a wrong seat itself with 403, or an unknown player with the same 404 a missing session returns, and a key that fires anyway is logged at warning level with its constraint name and rethrown as a server fault, because it means a check above it was missed. Checking first is sound only because a seat never moves once seated — the column is mapped non-updatable — so unlike seat *allocation* there is no window to narrow. Each index maps to one exception, proved by driving the adapter through a live schema rather than a stub: `uq_hand_session_seat` becomes `HandAlreadyDealtException`, `uq_trick_session_sequence` `TrickAlreadyOpenException`, `uq_trick_play_trick_seat` and `uq_trick_play_trick_player` both `AlreadyPlayedInTrickException` — one player makes one play whichever index catches the second — and `uq_trick_play_trick_card` `CardAlreadyPlayedException`. Three details of that test are load-bearing: cards come from the seeded catalogue, because the domain's deck fixture mints synthetic identifiers `fk_hand_card_card` refuses; the class is not `@Transactional` and cleans nothing up, since the first violation marks a test-managed transaction rollback-only and would poison every later assertion, so each case mints its own identifiers and commits as production does; and two indexes must be reached deliberately, `uq_hand_session_seat` by nulling the leader seat *and* dealing fresh hand identifiers, because reusing them makes `saveAndFlush` merge and silently succeed, and `uq_trick_play_trick_card` by inserting a `hand_card` row by hand, since the adapter's own delete refuses the second play first. The negative controls are that a deal naming an unseated player, and one naming a seated player at somebody else's seat, each write *nothing*; and what the test cannot reach is recorded in it — the missing-card server fault, while the foreign keys make a referenced card undeletable, and both seat backstops, because the adapter refuses first, so a fired backstop's warning line is untested by construction. Two reads also turn out to throw `InvalidDataAccessApiUsageException` and not the JPA-specification `IllegalStateException` they appear to, because the adapter is a `@Repository` and Spring translates on the way out; both still fall to the catch-all 500, and the assertions pin that, since an `IllegalArgumentException` would render as a 400 and blame the caller for a fault of ours. Reading the leader seat revalidates the column against the domain's seat count, and a seat bound for a column is refused at the boundary rather than left to the CHECK; both guards are pinned as the pure functions they are, the read guard because it cannot be reached end to end at all — this slice's range constraint refuses the very row the guard exists to survive — and the write guard because only its negative limb is out of reach. The three range constraints carry preconditions that halt with the query to run instead of an engine error naming neither the row nor the reason. A security review rejected the slice for documentation claiming an authorisation this layer does not perform: it authorises nobody, none of its statements takes a player identifier, and the seat check is a check on the *row* rather than on the requester. [ADR-024](docs/adr/ADR-024-trick-play-persistence-boundary.md) now carries that decision, the argument behind it, and the obligation it puts on Slice C2 — authorise the requester first, in every use case, because no test here fails if you do not. This slice's documentation work landed with it: ADR-024 was created, and ADR-023, ADR-020, ADR-013, `docs/adr/README.md`, `docs/architecture/C4-Diagrams.md` and `docs/architecture/runtime-view.md` were corrected, because mapping the five tables falsified standing claims in three documents that the tables were unreachable — the containment is now the absence of a use case and a route rather than the absence of a mapping
- The use cases that drive trick play: `DealHandsUseCase`, `PlayCardUseCase` and `ResolveTrickUseCase`, plus the `DeckShuffler` port and its `SecureRandomDeckShuffler` implementation, a third `findWholeDeck()` method on `CardRepository`, and two new domain exceptions with their 409 mappings — all three use cases wired in `UseCaseConfiguration` behind `eop.features.trick-play`, off by default (EOP-14, ADR-025). Slice C1 shipped ports that could reach five trick-play tables and no bean that did; this is the slice that adds the beans, which is why the flag is a merge precondition rather than a nicety, and `TrickPlayDisabledIntegrationTest` asserts all three beans are *absent* with the flag off rather than asserting 404s, because a route does not exist yet and asserting absence pins the mechanism instead of a symptom. Nine decisions are worth naming. **Dealing is its own use case rather than a step in starting a session**, and this is a chosen seam rather than a forced one — an earlier version of this entry and of ADR-025 claimed it was forced, and an architecture review refuted the claim. What is true is that `recordDeal`'s conditional update requires the status transition to have been *written* first, not committed, because a transaction reads its own writes; and that the use-case layer may not demarcate a transaction itself, since that would need `org.springframework.transaction` in a layer required to have no Spring import at all. What does not follow is impossibility: a `@Transactional` method in the outer ring calling start and then deal joins both adapter writes into one transaction through the `REQUIRED` propagation they already carry, with no import added to `usecase`, which is where Clean Architecture puts demarcation anyway. That composer is declined on cost, and the cost is nothing to do with imports — `StartSessionUseCase` publishes `GAME_STARTED` over SSE during its own execution, so a composed transaction broadcasts a start that a rolled-back deal then unmakes, trading a recoverable inconsistency for an unrecoverable one; making it safe needs publish-after-commit, which is a larger design than the window it removes and belongs in its own ADR. The started-but-undealt window that leaves is accepted and recoverable, because `recordDeal` writes the leader seat only where none is recorded, so a retry is free and idempotent — recognising that state is the route slice's work, and ADR-025 records the alternative of one start-and-deal endpoint as deferred rather than rejected, which stays available precisely *because* the deal is its own class. **Authorising the requester is the first port call of all three**, since the ports take no acting player and say so: beneath them a conditional update that matches no rows re-reads the session and answers one of five distinguishable states, which is the right candour for a member and an oracle for a stranger, so each use case has a test asserting a stranger is refused **before any hand is read** — the assertion is on the repository double's read log, because a refusal that has already read is a refusal that has already leaked timing. **`PlayCardCommand` carries no seat, no player identifier, no suit and no rank.** Each is derivable from something the caller cannot choose — seat and player from the identity token, suit and rank from the deck row — and the two defects a security review found in Slice A were exactly a caller-supplied seat and caller-supplied suit and rank, so they are now inexpressible rather than validated, which is a stronger guarantee than a rule somebody has to remember to write. **No use case pre-checks a state its conditional write already arbitrates**: a status or already-dealt check would read state, let go of it, then write, which is an illusion of safety and duplicates ADR-020's compare-and-set — the defence in depth that is real here is *the use case authorises identity, the port enforces state atomically*, two different questions rather than one asked twice. **Two pre-flight guards exist only to order a refusal before a commit**, and neither is an authority: `hand.resolve(card)` and a leader-seat comparison run before `openTrick`, because `openTrick` commits a trick row and `Trick.acceptPlay` would refuse *afterwards*, leaving an open, empty trick nobody asked for and no later slice knows how to clear. At the end of a hand every hand is empty, so without the first guard a caller would receive an `IllegalStateException` — a 500 — for what is properly a 422. `Trick.acceptPlay` still re-checks both and still owns the answer. **The deal returns `void`**, because a result carrying every hand is precisely the shape that leaks private information — the reason `Hands.toString()` names no card — and a facilitator has no more right to see the table's cards than anyone else; a player reads their own hand through a query of its own in a later slice. **Only the facilitator may deal, but any seated member may resolve a trick**, because resolution is a mechanical consequence of the last card and gating it on one person would stall a table whose facilitator's connection dropped. **None of the three broadcasts anything, which makes them the first writes in the system that change what every player can see and tell nobody.** No use case here takes a `SessionEventPublisher`, and no `SessionEventType` constant is added, deliberately: that constant carries the name appearing in the `event:` field of an SSE frame, the name is fixed by `docs/api/openapi.yml` under contract-first (ADR-004), and minting one in a slice that publishes no contract would only guarantee a rename when Slice D writes it. Until the broadcast is wired a client learns of a deal, a play or a resolution **only by re-reading**, so the stream stays silent for the whole of a trick — Slice D owned the wire names and Slice E passed the publisher in, so all three names are emitted as of that slice; nothing in the repository failed while it was missing, which is why it is a numbered decision in ADR-025 and not only a line in a handoff. **The pre-flight ordering above is an argument rather than a mechanism, and its scope is now written down**: it holds by exhaustion over the refusals `Trick.acceptPlay` has today, since on an opening play no suit has been led and the trick is empty, and the refusals that could still fire are each pre-flighted before the write. Any refusal added to `acceptPlay` — or to `Trick`'s constructor, which carries nine of its own — reopens the orphan-trick window silently, from a class that never mentions trick rows; the durable fix is to persist the trick and its first play in one call, which changes the `TrickRepository` contract. Two smaller things carry reasoning too: `NoTrickToResolveException` and `TrickNotCompleteException` are separate types answering 409, joining `HandNotDealtException` to make three too-early states with three titles, because a client that says "waiting for the deal" rather than "waiting for the lead" rather than "waiting for a player" cannot tell them apart from one shared answer, and all three are retryable; and the shuffle is a port rather than a `java.util.Random` parameter so the security-relevant choice of source is made once in an adapter and cannot be weakened by a caller passing a seeded generator, with `Hands.deal` staying deliberately pure so every use-case test above it gets a permutation it can predict. `ResolveTrickUseCase` also gives `WinningPlayNotInTrickException` the only thrower it will ever have — unreachable through `Trick.resolved()` today, written because `fk_trick_winner_play` confines a winning play to the `trick_play` table and nothing narrower, and the composite key that would confine it cannot be expressed in Liquibase. Where a hand has run out of cards the resolution wrote the winning seat as the next leader, because the port took an `int` and rejected anything outside seat range; it was harmless while no seat holds a card, both branches were pinned by tests, and Slice E was the slice that learned to recognise the end of a hand — the parameter is now an `OptionalInt` and a played-out hand records no leading seat at all

The test that pins this sends a body naming an impostor's `seatOrder` and `playerId` and a forged `suit` and `rank`, gets a 201, and asserts all four values in the response came from the token and the deck instead. **The trick published back says nothing about whose turn it is, whether the trick is complete, or which seat leads next**, because all three depend on which seats still hold cards, which is not part of a trick and which the use cases do not return; reporting them from a controller would mean either guessing or reaching past the use case into a repository. The consequence is stated rather than hidden: **the flag cannot be flipped until a later slice adds a read that exposes them**, because with only one's own hand and the trick returned from one's own play, a client cannot learn whose turn it is. (2026-08-14, EOP-14 Slice E: that consequence is discharged, and the sentence above is kept because it records why the flag stayed down through Slice D rather than because it is still true. The bullet below adds `GET /api/v1/sessions/{sessionId}/tricks/current`, which publishes all three of those answers and `handComplete` besides. It is `Boolean` now, with a compact constructor collapsing absent and explicit null to `false` so nothing downstream sees a third state, and the same constructor copies the component list, which refuses a null entry at the boundary — the one shape `@Size` waves through. Both were found by a test asserting the contract, not by the compiler. **The controller logs nothing, and that is the deliberate choice ADR-026 asked for.** These are the first routes through which dealing and playing can be invoked, so the observability gap stops being theoretical, but ADR-026 is `Proposed` with four arrangements still to weigh and one of them is "log at the boundary only" — adding a logger here would adopt that option inside a feature slice and make one controller the sole observed entry point. A test reads the contract as text and fails if the Java enum and the YAML enum drift. Two things are recorded honestly rather than fixed here. Unknown request fields are **accepted and ignored** repo-wide, not refused — refusing them would be stronger, but the setting is global to every endpoint and belongs to a decision of its own; the defence in the meantime is that no forged field is read, which the 201 test proves field by field. And `NotFacilitatorException` answers a refused deal with the title `Only the facilitator can start play`, which is accurate about the rule and vague about the action. - The state of play, the end of a hand and the trick-play broadcast: `GET /api/v1/sessions/{sessionId}/tricks/current` with `GetTrickStateUseCase`, the `TrickState` result and the `TrickStateDto` transport record, publishing `seatToPlay`, `complete`, `nextLeaderSeat` and `handComplete` (EOP-14, ADR-014, ADR-020, ADR-023, ADR-027, ADR-028). - The scoring rule as pure domain types: `ScoredPlay`, `Standing` and `ScoreSheet` under `org.maglez.eop.entity`, with zero framework imports, computing the score of a game from the tricks already played (EOP-15, ADR-030). No schema, no route and no use case ships with them — this is the rule on its own, provable without any of that, and `ScoreSheet.of(players, tricks)` is a pure function whose whole input is a seating and a list of tricks. Seven decisions are worth naming. **The score is derived and never accumulated.** There is no running total anywhere, no counter column and no increment on the play path, because a stored total is a second authority that can disagree with the plays that produced it, and the moment it does there is no way to tell which of the two is the game. Deriving it also settles what the ticket's "computed and stored server-side" is really protecting: the constraint is about *authority* — the client never asserts its own score — and a derivation satisfies that more completely than a stored figure a write path could get wrong. **The rule is one point for a threat connected to your own card plus one for taking the trick, and it must not be embellished.** The richer system the deck's author tried — four for a threat on your own card, three, two and one for threats on other people's, plus bonuses for face cards and aces — was abandoned because playtesters could not compute it at the table and looked to the facilitator at the end of every round to be told who had scored. That constraint does not bind a server, so a richer rule is cheap to add later and is recorded as an option; it is deliberately not built here, because shipping the simple rule first is what makes the digital form's advantage measurable rather than assumed. **A linked threat that names no component still scores.** `TrickPlay`'s Javadoc left this open for this story to settle, and it settles it in favour of scoring: the written rule keys on the threat being connected, not on a text box being filled; the application holds no model of the system under discussion (PRD §3.4) and therefore *cannot* validate a component name, so making a point conditional on one would make the score depend on unvalidated client free text, which is exactly what "a client must never assert its own score" forbids; and the printed Score Card's Component(s) column is legitimately blank on plenty of real rows. **The two points a row can earn stay separate rather than pre-summed.** `ScoredPlay` carries `threatPoint` and `trickPoint` as distinct booleans because the Score Card is read by humans mid-game who need to see *why* a row scored — a row scoring one point because the threat landed looks nothing like a row scoring one point because the card took the trick, and a single `points` field makes the two indistinguishable at exactly the moment somebody queries the total. A play with no threat linked that still takes the trick is an ordinary row, not an anomaly. **Ties are shown as ties and never broken.** Standings use competition ranking, so four players on 7, 5, 5 and 2 hold positions 1, 2, 2 and 4, and `Standing.tied` is published even though a caller could derive it, because the interesting fact about a shared position is that it is shared. There is no tie-break rule to get wrong later because none is invented now. **A display name is never a key.** `DisplayName` is free text, unverified and explicitly not unique — two people at the same table may choose the same name and the humans on the call disambiguate them — so every row and every standing keys on `playerId` and carries the name for rendering only. `pointsOf` takes a player identifier and refuses a stranger rather than answering zero, because zero is a legitimate score and silently returning it for somebody not in the game would be a plausible lie. **An unresolved trick contributes threat points but no trick point.** The trick list may end with a trick still on the table, and the sheet scores its plays' threats while awarding nobody the trick, which makes a running score monotone as play proceeds — a total can never fall — and means the same class serves the mid-game read and the final standings with no second code path. Deciding that the game has *ended* is not this class's job and it does not try: it reports the score of the tricks it was given, and the session owns the transition to `COMPLETED`

### Fixed

- **`POST /api/v1/sessions` was unbounded: an unauthenticated caller could flood the join-code keyspace and exhaust the database (EOP-19, ADR-033).** Creating a session requires no credential and inserts a permanent row. Without a limit, a single caller could fill the `game_session` table at network speed — at 500 req/s that is 43 million rows per day — consuming every six-character join code and causing legitimate facilitators to receive opaque 503s once the five-attempt collision retry exhausts. Three controls now bound the attack surface. **Session creation limiter:** `POST /api/v1/sessions` is rate-limited to `eop.web.session-creation-limit` creations per address per 60-second sliding window (default 5). The slot is reserved atomically *before* any database work via `SessionCreationLimiter.recordCreation`, so a refused request never commits a row; if the downstream use case fails after the slot is reserved, `refundCreation` returns it so that a transient error does not permanently consume a creation allowance. The limiter is fail-closed on saturation: when the tracked-key table reaches 10 000 entries and a new address arrives, the attempt is refused before any database work rather than silently admitted — a flood of distinct keys is itself an attack pattern. **Request body cap:** Caddy enforces `request_body { max_size 16KB }` on all `/api/*` routes, rejecting oversized bodies at the proxy before they reach the application. This is the only body-size layer; there is no application-side cap, and direct access to port 8080 (bypassing Caddy) is unprotected — a known and accepted limitation recorded in ADR-033. **Neutral exception type:** the new `RateLimitedException` (use-case layer, no Spring imports) carries `retryAfter()` and produces a problem detail with title `"Too many requests"`, accurately describing a creation throttle rather than the join-attempt vocabulary the previous implementation reused. `GlobalExceptionHandler` maps it to HTTP 429 with a `Retry-After` header. The join-attempt limiter is unchanged and continues to throw `TooManyJoinAttemptsException`. **Configuration:** the limit is bound via `TrustedProxyProperties` (`@ConfigurationProperties(prefix = "eop.web")`), which already owns the `eop.web` namespace; `sessionCreationLimit` is a new `@Min(1)` field with default 5. The test suite overrides it to `Integer.MAX_VALUE` in `application.properties` to prevent exhausting the limiter across the shared Spring context; a dedicated `@SpringBootTest(properties = "eop.web.session-creation-limit=1")` scenario exercises the 429 path through the full HTTP stack. **Accepted limitations:** the counters are in-process memory and are forgotten on restart (a restart is a deployment, not something an attacker can trigger); horizontal scaling multiplies the effective limit by the instance count (there is one instance, ADR-012); NAT'd users share one bucket; and address rotation sidesteps the per-address window. All four are recorded in ADR-033

- **`InMemoryJoinAttemptLimiter` was fail-open on saturation and non-atomic on check-and-record (EOP-18, ADR-019).** Two independent defects. First: when either map reached `MAX_TRACKED_KEYS = 10 000` entries and a new key arrived, the old `remember()` silently returned without recording or refusing — a new address was admitted with no counter, so the ten-failures-per-address limit never fired for it. Second: `checkAllowed()` and `recordFailure()` were separate non-atomic operations; two concurrent threads both at `limit - 1` could both pass `checkAllowed`, both proceed to the database, and both record — so the effective limit was `limit + concurrency - 1` rather than `limit`. Both defects are now closed. **Fail-closed on saturation:** `checkAllowed` now calls `checkSaturation` for both maps before any database work; if a map is full and the key is new, it first attempts to evict windows whose entries have all aged out of the sliding window, and if the map is still full after eviction it throws `TooManyJoinAttemptsException` immediately. `recordFailure` silently drops the record for a saturated map — the key stays untracked while the table remains saturated, so this caller's subsequent attempts are refused by `checkAllowed`'s saturation check. **Atomic check-and-record:** `recordInWindow` acquires `synchronized(window)` on the deque before pruning, checking the allowance, and appending the new timestamp; this is the only site that mutates a window deque. `checkAllowed` is a best-effort pre-check that takes no lock on the window deques; it may evict aged-out map entries via `evictEmptyWindows` (a map mutation, not a deque mutation), and avoids database work for clearly over-limit callers. **Both windows always evaluated:** `recordFailure` records in both the address window and the code window regardless of which one is saturated — silencing the per-code counter under address-table saturation would disable the control that defends against a distributed enumeration attack. **Port contract updated:** `JoinAttemptLimiter.recordFailure` now declares `@throws TooManyJoinAttemptsException` to match the implementation. Three documents updated to reflect the new behaviour: `docs/architecture/C4-Diagrams.md`, `docs/architecture/runtime-view.md` and `docs/adr/ADR-019`

- **Two reachable exceptions had no mapping, so ordinary seat contention answered 500 with a stack trace.** `JoinSessionUseCase` retries a contested seat up to `MAXIMUM_SEAT_ATTEMPTS` times and then rethrows the last `SeatAlreadyTakenException`; `CreateSessionUseCase` rethrows `JoinCodeUnavailableException` after five consecutive join-code collisions. Neither had an `@ExceptionHandler`, so both fell through to `handleUnexpected` — 500, plus a full trace at ERROR, on a path that is not a malfunction at all. `GlobalExceptionHandler` now maps `SeatAlreadyTakenException` to **409** and `JoinCodeUnavailableException` to **503** with `Retry-After: 5` (EOP-17, ADR-005, ADR-019). Four decisions are worth naming. **Neither response echoes its exception's message.** `SeatAlreadyTakenException` builds its message from the session UUID and the seat order, and a joining caller supplies only a join code — so returning `getMessage()` would hand back an internal identifier the caller never held; `JoinCodeUnavailableException`'s message describes our own generator colliding with our own data, which is of no use to someone who never sees a code being generated. Both handlers therefore set a fixed detail, following the precedent already set for an unknown join code. **The two paths log at different levels, and that asymmetry is the point rather than an inconsistency.** Seat contention is provokable at will by anyone holding a valid join code — roughly twenty concurrent joins against one lobby will do it — so it logs at DEBUG *without the throwable*: mapping it to 409 while still writing a WARN and a stack trace per occurrence would have relocated the log-flooding amplifier instead of removing it, and the flooding is half of what this ticket exists to fix. Join-code exhaustion cannot be provoked, needing a run of independent collisions across the whole attempt budget, so each occurrence is genuine evidence that the live-lobby count is approaching what a thirty-bit code space bears, and it logs at WARN with the throwable — the handler being the only place that evidence ever appears. Neither logs at ERROR, which is what the acceptance criteria asked for, and the tests assert the level and the absence of a `throwableProxy` rather than only the status, because a status assertion alone passes just as well against a handler that logs at ERROR. **The 503 is a capacity statement, not an error**, which is why it carries `Retry-After` like the 429 does and why five seconds is documented as a defensible guess rather than a derived figure: there is no queue draining at a known rate to compute it from, and it only has to be short enough that a facilitator retries and long enough that a client honouring it does not immediately re-run the same exhausted loop. **The unit tests could not have caught what escaped.** What reached `main` was not a wrong handler but an absent one, and an absent handler is invisible to a test that names the handler it expects — so `SessionContentionIntegrationTest` drives both paths through the full web adapter and proves Spring dispatches to the new methods rather than to the catch-all, using a `@Primary` decorator over `SessionRepositoryAdapter` with two independent switches because neither path can be provoked honestly and filling the lobby to six raises the already-mapped `SessionFullException` instead. Its third test creates and joins with both switches closed, guarding the acceptance criterion that untouched paths stay untouched. The shared `Conflict` response in `docs/api/openapi.yml` now enumerates fourteen titles rather than thirteen, the count having been wrong in the direction the prose itself warns about, and a new `ServiceUnavailable` response documents the 503. It had propagated to one other place that still carried it — the story template in `.opencode/agents/product-owner.md`, which named `ff_feature_name_v1` in its flag strategy and in both Gherkin scenarios, so every story written from it would have carried a flag name the rule now bans; that template is corrected here too. It also directed the reader to catalogue flags in `docs/feature-flags.md`, a file that does not exist — flags are recorded in `application.yml` beside their defaults and in ADR-013, and the rule now says so
- **The ADR index disagreed with two of the ADRs it indexes.** ADR-002 had been amended on 2026-07-27 and ADR-012 on 2026-08-10; the index showed the first as plainly `Accepted` and the second as `Accepted (amended)` with no date. An undated amendment reads as current, and a missing one reads as unamended, so the index was quietly overstating how settled two decisions were. Both rows now carry the substance and the date. Because the index has drifted twice for the same reason — keeping it in step is step 5 of a manual checklist — `AdrIndexConsistencyTest` now fails the build when an ADR has no index row, a row links to a missing file, an ADR does not carry exactly one `**Status:**` line to compare against, a status word disagrees, or a dated amendment reaches the index without its date. The invariants are deliberately narrow: a test strict enough to dictate wording would be worked around rather than obeyed
- **`X-Forwarded-For` was believed from any caller, so the join-code throttle could be bypassed by rotating one header.** The application read the last entry of the header and used it as the client address — the key the join-attempt limiter counts failures against. The reasoning was that Caddy is the only published entry point (ADR-017) and Caddy appends to the header, so the last entry is the one the proxy wrote: sound, but valid only if the peer really is the proxy, and nothing checked that. Reached directly — by `./mvnw spring-boot:run` on port 8080, from a sibling container on the Compose network, or through any later change that publishes the application port — a caller supplied its own rate-limiter key, and a fresh value per request meant a fresh empty bucket per request, so the ten-failures-per-address limit never fired. The per-code counter could not compensate, because a code-guessing attacker uses a different code every time. ADR-019 designates that limiter a *primary* security control rather than defence in depth — a six-character join code is thirty bits, unguessable only while guessing is slow — so this was not a thinned-out layer but the removal of the control the entropy budget was calculated against (EOP-26, ADR-021)
- **Trust in a forwarding header is now an explicit, default-denied allow-list.** `eop.web.trusted-proxies` holds literal addresses or canonical CIDR blocks; the header is ignored entirely unless the peer address is on that list, and the default is empty, so an application deployed without a thought about forwarding headers trusts nobody and keys on the peer. A malformed or non-canonical entry fails startup rather than being skipped — silently masking `10.0.0.5/8` to `10.0.0.0/8` would trust sixteen million hosts where the author plainly meant one. Every resolved address is canonicalised before it becomes a map key, because two spellings of one address are two buckets, which is the same defect arriving by another route. `server.forward-headers-strategy` is pinned to `none` in both profiles so neither Tomcat's `RemoteIpValve` nor Spring's `ForwardedHeaderFilter` can launder the header into `getRemoteAddr()` behind the check: their default trust lists cover `172.16.0.0/12`, which contains this project's own Compose subnet. The deployed value sits beside the proxy's pinned container address in `compose.app.yml`, so the two halves of one fact cannot drift apart (EOP-26, ADR-021)
- **A green build had been evidence that the bug was still present.** The integration suite's `freshAddress()` helper gave each test its own throttle bucket by setting `X-Forwarded-For` — a test choosing its own rate-limiter key from outside the process, which is precisely the attack. The suite had been getting its isolation *from the vulnerability*, so closing the hole broke sixteen previously-passing tests. Trusting `127.0.0.1` suite-wide would have let all sixteen pass unchanged and was rejected: it would have re-opened the hole everywhere in the suite except in the tests that assert it is closed. The helper is now `unusedAddressHint()`, documented as having no effect, and the throttling tests get a fresh limiter from `@DirtiesContext` instead of from a forged header (EOP-26, ADR-021)

### Known issues

- **k6 results never reach InfluxDB, so the Grafana dashboard is empty.** Three independent causes: the sample environment pointed at a container hostname (fixed here); direnv exports `.env` at directory entry so an already-running shell keeps the stale value; and InfluxDB has HTTP authentication enabled while the k6 output URL carries no credentials — a direct write with the configured admin credentials returns `401`. k6 logs one write error per flush interval but **exits 0**, so thresholds still gate correctly and nothing checking the exit code ever noticed. The JSON and summary files written to `docs/performance/history/` are the real evidence. Repair needs its own story

### Decided, not yet implemented

Recorded here so that a decision is never mistaken for working code. Each of these
has an accepted ADR or rule file but no implementation in `src/` or `pom.xml`.

- Configuration management via `@ConfigurationProperties` + `@Validated` — rule only, no such class exists
- Resilience patterns: Resilience4j retry, circuit-breaker and time-limiter — `.opencode/rules/resilience.md` records the intent, but the dependency is absent from `pom.xml`
- Automated deployment: the pipeline publishes a deployable image but does not deploy it. Rolling the new tag onto the instance is a manual pull-and-restart over SSH (ADR-012 records why CI-driven SSH deployment is deliberately avoided)
