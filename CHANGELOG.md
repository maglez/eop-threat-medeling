## [1.0.0-SNAPSHOT] — Unreleased

### Removed

- **Ace cards removed from the deck — deck size is now 68 (EOP-75, ADR-041).** The six Ace cards (one per STRIDE suit, rank 14) do not appear in the physical printed Elevation of Privilege card game. The committed card artwork (`ui/src/assets/cards/`) contains exactly 68 PNG images with no Ace in any suit, confirming the physical deck. `Rank.ACE` (value 14) has been removed from the `Rank` enum; `Card.isOpenThreat()` has been removed — the Open-Threat concept does not exist in the physical game. The Liquibase migration `2026-08-18--remove-ace-cards.xml` deletes the six Ace rows. King (rank 13) is now the highest rank. ADR-041 records the decision and resolves the conflict between the author's "74 cards" quote in `LICENCE-eop-deck.md` and the committed card images. ADR-023 deal arithmetic is re-derived for D = 68.

- **`VITE_LOBBY_UI_ENABLED` feature flag removed — lobby UI now always on (EOP-77).** The `VITE_LOBBY_UI_ENABLED` build-time flag introduced in EOP-11 has been removed per `.opencode/rules/feature-flags.md` (flags are removed once the feature is stable). The Create and Join session buttons in `HomeView` are now always enabled. The `isLobbyUiEnabled` constant and its guards have been removed from `App.tsx` (both the `useState` initializer and `HomeView`). `VITE_LOBBY_UI_ENABLED` has been removed from `ui/src/vite-env.d.ts` and `ui/.env.example`. The `lobby-ui: false` documentary entry has been removed from `application.yml`. Flag-specific tests in `App.test.tsx` have been removed; the remaining session-reconnect tests no longer stub the flag. ADR-037 Consequences has been amended to record the retirement and to name `VITE_GAME_SCREEN_ENABLED` as the current live example of the pattern.

- **`Rank` enum reduced from 13 to 12 values (EOP-75).** `TWO(2)` through `KING(13)`. `Rank.ofValue(14)` now throws `IllegalArgumentException`. The OpenAPI `Rank` enum is updated to remove `ACE`; `rankValue.maximum` is updated from 14 to 13.

### Fixed

- **Two rule files asserted things the repository contradicts, and a third fiction was found in the same passage (EOP-36, ADR-044).** `.opencode/rules/*.md` is injected into every agent's context every session, so a false rule is read on every turn — the defect class EOP-32 opened and this story closes. Three fixes, no production code touched. **First, `resilience.md` opened by mandating Resilience4j** — `@Retry`, `@CircuitBreaker`, `@TimeLimiter`, config per profile — for a dependency that is not on the classpath at all: `grep -rn 'resilience4j' pom.xml src/` returns nothing, and there is no annotation and no `resilience4j.*` block in either profile file. Of the two legitimate fixes the ticket offered — adopt the library, or disclose its absence — the evidence forces the second, and forces it more strongly than the ticket knew. Resilience4j guards calls that *leave the process*, and this application makes none: there is no `RestTemplate`, `WebClient`, `RestClient`, `HttpClient` or Feign client anywhere in `src/main/java/`, and the only outbound dependency is the database via Spring Data. Adopting it now would ship an unused dependency — supply-chain surface for zero benefit. The file now leads with that disclosure and keeps the seven rules below it as *how resilience must be introduced*, explicitly marked as not describing anything in place. Three further precisions the ticket did not ask for: resilience is in a **weaker** position than caching, not an equal one — `caching.md`'s parallel disclosure sits above a `spring-boot-starter-cache` that is genuinely on the classpath (`pom.xml`) waiting to be switched on, whereas resilience has no library at all, so adopting it starts with a dependency and therefore an ADR rather than an annotation; `SessionResilienceIntegrationTest` is named closely enough to be mistaken for coverage here and is not, exercising in-process session robustness and importing nothing from Resilience4j; and `CHANGELOG.md`'s "Decided, not yet implemented" entry and this disclosure must now move together, so adoption deletes both in one change. The final rule also carried the multi-profile fiction EOP-32 removed — config "externalised per profile" — which would have reintroduced the exact defect that story eliminated; it now names `application.yml` and `application-prod.yml` as the only two profiles that exist and forbids the "per profile" phrasing outright. **Second, `database.md` prescribed a changelog naming scheme six of the nine files on disk do not follow**, and the fix is the opposite of the ticket's instruction in two places. The ticket said to describe the scheme actually used; the scheme actually used is *both*, and they are not interchangeable. `<includeAll>` orders by filename with no manifest and no ordering attribute, so execution order **is** alphabetical order — confirmed by reading the changesets Liquibase reported during `DeckTrimMigrationRoundTripTest` rather than assumed — and authorship order matches it today only because ASCII `0` sorts before `2`. A `007-` file, the obvious next step for anyone reading the six legacy names as a live sequence, would therefore execute **before** all three dated migrations, ahead of schema its DDL may depend on, with a green build everywhere already migrated past it. So the dated scheme is declared the forward convention and `NNN-` is frozen at `006-`; the legacy six keep their names permanently, because a filename is part of changeset identity and renaming one orphans rows in `DATABASECHANGELOG` on every environment that is not a fresh database. The ticket also asked for the `id` bullet to be rewritten from per-file numbering to global, on the evidence of `002-real-deck.xml` carrying `003-`/`004-`. Checking all nine files falsifies that: **eight of nine restart at `001`**, so the rule was already right and the requested change would have made it wrong for eight files to fix one — the same defect class inverted. The bullet now documents the practice, names the outlier as legacy that Golden Rule 1 forbids renumbering, records both acceptable `id` styles, and shows `006-session-expiry.xml`'s per-database variant pattern. **Third, an unticketed fiction in the same passage:** the rule quoted the master changelog as `<includeAll path="classpath:db/changelog/changes/"/>`, an absolute form the repository does not use and which previously resolved to **zero** changesets in silence — unnoticed while the directory held only a `.gitkeep`, because an empty changelog and an unreadable one are indistinguishable until the first migration exists. An agent copying that snippet would have reintroduced a migration setup that reports success and runs nothing. The real `relativeToChangelogFile` / `endsWithFilter` form is now quoted with both attributes marked load-bearing. The ordering proof, the frozen-identity argument and the `classpath:` history live in [ADR-044](docs/adr/ADR-044-changelog-file-naming-is-dated.md) rather than in the rule file, following the placement precedent ADR-043 set one story earlier: a hot-path artefact pays for its length on every turn, so the rule keeps the directive and the one-line reason and the evidence goes where it can be dated and superseded. Two limits stated plainly. **Nothing enforces the naming scheme** — no test asserts that no new `00N-` file appears, and none is added, on scope discipline alone: the ticket carries an explicit warning that widening scope on this family "buys a fourth round rather than a better repo", and a review-enforced convention is proportionate to a hazard nobody has yet triggered. An earlier draft of this entry also claimed such a guard would need an allow-list of the frozen six that "would itself go stale"; the architecture review falsified that, and it is corrected rather than left standing — the freeze is permanent and Golden Rule 1 forbids renaming any of the six, so the allow-list would be a *constant*. A justification that inverts its own premise is precisely the defect class this story removes, one remove out. The `007-` hazard is therefore closed by convention and review, not by the build. And the dated name is the date of *authorship*, not of merge, so the scheme guarantees ordering against the legacy block unconditionally but ordering among dated files only while authorship order and merge order agree — two migrations with a genuine dependency should not be in flight on separate branches. Three further review findings were remediated in the same story rather than deferred, all of them the story's own defect class turned on itself: `resilience.md` cited `spring-boot-starter-cache` as `pom.xml:56`, and a bare line number into a moving file, held in a hot-path rule file with no guard, is the rot vector that invalidated ADR-023's `**Amends:**` citations in EOP-93 — it now cites the artifactId alone, matching `caching.md`'s better model; and `docs/devops/local-development.md` turned out to be a **second** place prescribing the naming scheme, correct but carrying neither the `007-` freeze nor a link to ADR-044, with an adjacent "changelogs are applied in order" that now names the order as alphabetical. A convention documented in two places with the reason in only one is how the next drift starts.

- **Nine places stated a round-trip count, a trick count or a hand size derived from a deck size two trims out of date (EOP-96, ADR-031 amended).** Five of them claimed that assembling the score one trick at a time would cost seventy-nine round trips at three players. That figure is `1 + 3 × 26`, and twenty-six tricks is `ceil(78 / 3)` — a 78-card-era number, stale since EOP-69 took the deck to 74 and untouched by EOP-75 taking it to 68. It survived both trims and EOP-93's nineteen-site sweep for the same reason: it is a figure **derived** from the deck size rather than the deck size itself, so a sweep looking for `74` and `78` never saw it. The correct cost at 68 cards is `1 + 3 × 23` = 70, because a three-player deal is 23/23/22 and a hand runs to `ceil(68 / 3)` = 23 tricks. Corrected in `ADR-031` section six (which also contradicted its own ADR-023 links entry, already correct at 23 tricks), the ADR-031 row of `docs/adr/README.md`, the `TrickPlayRepositoryAdapter` sequence note in `docs/architecture/runtime-view.md`, and the production javadoc on `TrickPlayRepositoryAdapter.findTricks` — a stale claim about the cost of the alternative design, sitting in the code that embodies the chosen one. Four further sites the ticket had not listed were found by sweeping for the derived figures rather than the deck size: `SeatAndSequenceBoundsTest` inserted trick sequence `26` and called it "a high sequence" (it now inserts 1, 23 and 999, so the absence of an upper bound is actually demonstrated rather than asserted against a legal game length), the `<comment>` on migration `005`'s trick-sequence changeset, and two `## [Unreleased]` entries in this file. Wherever a number is now stated the derivation is stated with it, so the next deck change makes the staleness visible instead of leaving a bare total to rot; where the count was incidental colour in a historical narrative it was dropped rather than re-derived. Editing a merged Liquibase changeset's `<comment>` is safe and does not violate ADR-008's immutability rule: `ChangeSet.generateCheckSum()` in the resolved `liquibase-core` 5.0.3 digests only `getChanges()` and `getSqlVisitors()` and never reads `getComments()`, verified by decompiling that class. The decompilation is the whole of the evidence, and deliberately stated that way: the green build cannot corroborate it, because every `@SpringBootTest` context reads the same new file into a fresh schema, so a comment-inclusive checksum would recompute identically and pass just as cleanly. Falsifying it would take replaying the old file and then the new one against one persistent database, which nothing in the suite does — and no test replays these migrations against PostgreSQL 17 or a pre-existing `DATABASECHANGELOG` at all. A green build is evidence that this changeset still applies, not that its checksum is comment-blind.

- **`DeckArithmeticClaimsTest` gained a third invariant: no round-trip count derived from a superseded deck size (EOP-96).** The guard EOP-93 added catches a stale deck size stated in Java prose, but 79 is not 78, so it was structurally blind to the defect above — which is a concrete instance of the limitation recorded in ADR-006: its matchers are phrase lists, not semantic analysis. The new invariant derives the figures it forbids (`ceil(size / 3)` tricks, `1 + 3 ×` that many reads, giving 79 for a 78-card deck and 76 for a 74-card one) so the next trim changes one number rather than a table of figures. Not *only* one number, though, which the first version of this invariant claimed and got wrong: prose states a total as a word, and a cost the guard cannot spell fails to match in silence rather than failing the build, so `spell()` has to know the word for the cost the current deck implies *before* the trim that makes that cost superseded. As shipped it did not — `seventy` was missing — which would have left the guard reaching one of the four corrected sites while its own javadoc promised all four. The spelling is now asserted rather than remembered, over the current deck size as well as the superseded ones. The invariant also strips Jira keys before reading any number, and fires only on a sentence that also costs out a read — `round trip` or `reads per trick`, the latter because the Mermaid note was the one site that never used the words "round trip". It is deliberately narrow, and two real lines forced that anchor: ADR-023's amended deal tables legitimately carry 78- and 74-card arithmetic, and ADR-011 line 44 has a standalone `26` in a sentence naming `graphify_query_graph`, so keying on "read" or "query" alone, or on trick counts at all, would flag prose that is correct. The anchor turned out to be the whole of what was needed. An earlier version of the invariant also skipped markdown table rows for the sake of those same two lines, which protected against nothing the anchor does not already prevent — neither line prices a read — while blinding the guard to the ADR-031 row of `docs/adr/README.md`, itself one of the nine sites this story had to correct by hand. Table rows are read again. A companion test pins seven literals the matcher must flag — four of them the real pre-fix sentences this story removed, the other three covering the figure in digits, the 74-card figure, and a sentence whose figure and anchor sat on different physical lines — alongside the corrected wording it must not flag; those literals are the only remaining copies of the stale figures in the repository, and quoting them is safe only there because `EXEMPT_FILES` already lists that file. Three gaps remain by construction and are not closed here: the guard scans `docs/**/*.md` and `src/**/*.java`, so it reaches neither the XML changeset comment nor this changelog — widening its roots would immediately flag every accurate historical entry above, including ones qualified by the deck size they describe. The third is older and wider than this story: the second invariant, which catches a superseded deck *size* rather than a figure derived from one, walks Java only, so nothing guards a stale deck size in markdown at all. The corrected sentences in ADR-031, `docs/adr/README.md` and the runtime view now name 68 cards and 23 tricks with no test standing behind them, which is the same shape of miss this story was raised to fix, one layer out.

- **Nineteen places still said the deck holds 74 cards, and four of them made an arithmetic claim that is false at 68 (EOP-93).** EOP-75 trimmed the deck from 74 to 68 by removing the six Aces (ADR-041) but left the old size stated in javadoc, ADRs and the PRD; two reviewers found some of them and the ticket listed those, and an exhaustive sweep found ten more. Nothing about the running game changes — every edit is a comment or a document. The dangerous half was not the digits. Several places asserted a *universal* claim over table sizes — "at 74 cards, **all four supported table sizes** (3, 4, 5 and 6 players) produce unequal hands", "at 74 cards **no** supported table size divides evenly", "wrong on the last trick **at every player count**" — and 68 divides evenly by four. So at a four-player table every seat holds seventeen, all seats exhaust together and the final trick is *full*: the claim is not merely off by six cards, it is false at one of the four table sizes, and it was false in the direction that matters because the worked examples had all picked four players as their illustration. Three of those examples were therefore unreachable arithmetic (`Trick.nextLeaderSeat`'s "seats 0 and 1 hold nineteen cards", ADR-023's "at four players two seats hold 19 and two hold 18", the PRD's "a win by seat 2 or 3 on trick eighteen") and are re-based on six players, where the deal genuinely is uneven. `Trick`'s claim that the winner-leads defect is "visible at every player count" is corrected too: at four players `nextLeaderSeat` returns empty rather than falling back to the clockwise seat, so the naive rule is harmless there. The correct figures at 68 are 23/23/22 for three players, 17/17/17/17 for four, 14/14/14/13/13 for five and 12/12/11/11/11/11 for six, and the suit counts are twelve per suit except Tampering at eleven (no 2) and Elevation of Privilege at nine (no 2, 3 or 4). ADR-023's terminal EOP-92 amendment block already stated all of this correctly and was left untouched; what had gone stale was the original body, four of the PRD's deviation blockquotes, ADR-019's quoted amendment, the ADR index row, and the concrete trick counts in ADR-030 and ADR-031. Correcting ADR-023's body in place rather than by a new amendment follows the document's own precedent — `git blame` shows EOP-69 rewrote those same paragraphs in place while also adding a dated block — and the genuinely historical references were left alone: ADR-041 records the trim, ADR-039 and the PRD carry dated "was 74, now 68" notes, `LICENCE-eop-deck.md` quotes the author's "74, not 78 cards", `DeckTrimMigrationRoundTripTest` needs 74 and 78 to assert the rollback path, and the merged Liquibase changesets may not be touched at all (`database.md` golden rule 1). The reason this needed a mechanical guard is that the same failure had just happened twice: EOP-92's review found three documents simultaneously stale against a green build, and EOP-93 is the same class. `DeckArithmeticClaimsTest` (new, in the `org.maglez.eop.docs` package alongside `AdrIndexConsistencyTest`) enforces two narrow invariants over every `docs/**/*.md` and `src/**/*.java` file. The first is the one worth having: within a single **sentence**, a universal quantifier over table sizes may not co-occur with a falsifiable claim about the deal being uneven, *conditional on* at least one supported table size actually dividing the current deck size evenly — a gate the test asserts is non-empty, so it can never pass vacuously. Sentence scope rather than line scope is deliberate, because markdown wraps prose freely and the one surviving true universal claim ("all four supported table sizes produce equal or near-equal hands") straddles two lines; a line-scoped matcher would miss the false version of exactly that shape. The second forbids a superseded deck size in Java prose, exempting only the rollback test and the guard itself, which must quote what it forbids or its regex becomes uncheckable. A third test feeds the three real pre-EOP-93 defective sentences in and asserts each is still caught, plus that the true-at-68 claim and the corrected wording are not — the guard's own anti-rot check, since a doc guard that quietly decays into a no-op fails in precisely the way it was built to prevent. It earned its place on first run by finding a defect that two eyeball passes and every `grep` had missed: `GlobalExceptionHandlerTest` constructed `new NoTamperingCardDealtException(78)` and asserted the response did not contain `"78"` — a deck size **two trims** out of date, invisible to text search because it is a numeric literal in code rather than prose. A third candidate invariant, "ADR-023's original body states no superseded deck size", was designed and then dropped: line 17 legitimately still reads 78 under EOP-69's explicit `**Amends:**` header, so it would have failed on day one against correct content, and an over-strict guard gets worked around instead of obeyed. Two figures were deliberately softened rather than re-derived, because neither source records how it was computed: `TrickControllerIntegrationTest`'s "about three times in a thousand" chance of a three-player hand missing a named suit becomes "a few times in a thousand", and ADR-031's "the seventy-nine reads a per-trick assembler would have cost" becomes "the read count". Two things surfaced in review and are fixed here rather than deferred. The sweep's own edits to ADR-023 shifted the file by three lines, which silently invalidated five line-number citations in EOP-69's `**Amends:**` header — a stale documentation pointer shipped against a green build, the very defect class this story exists to close, and one the new guard cannot see; that header now cites its targets by quoted phrase, which survives insertions above it as a line number does not. And because `DeckArithmeticClaimsTest` is the first of the three documentation guards to walk *all* of `docs/` and `src/` rather than a single named file, editing a Markdown document anywhere in the repository can now turn the build red. That is a change to what `verify` gates on, so it is recorded as a dated amendment in [ADR-006](docs/adr/ADR-006-build-quality-gates.md) and as a fifth gate in `.opencode/rules/build-quality.md`, together with the limits that matter to anyone trusting it: the matchers are phrase lists rather than semantic analysis, so a green build is not proof that the documentation is correct; invariant B has no exemption for historical amendment blocks, so if it ever fires inside one the fix is an exemption and not a rewrite of history; `ui/**` is outside invariant D; and if a future deck size is ever divisible by no supported table size the test must be deleted rather than left passing vacuously.

- **The deal discarded cards and biased the opening lead — every card is dealt again (EOP-92, ADR-023 amended).** EOP-72 replaced the whole-deck deal with equal hands and a discarded remainder. The product owner has withdrawn that requirement, so `Hands.deal()` deals the full deck once more and nothing is discarded: the round-robin loop runs to the end of the deck, the surplus of an uneven division falls to the lowest seats as a consequence of that order rather than as a separate rule, and 68 cards go out as 23/23/22 for three players, 17/17/17/17 for four, 14/14/14/13/13 for five and 12/12/11/11/11/11 for six. Previously a three-player table was dealt 22/22/22 and **two cards were destroyed every game**. The reason the product owner gives is that the opening lead belongs to whoever holds the lowest Tampering card, so discarding the remainder risks discarding that card and leaving the game unable to start. EOP-72 had in fact guarded against exactly that, but its guard carried a defect nobody recorded: it scanned for the lowest Tampering card and, when that card fell outside the kept range, swapped it to index `keptSize - 1` — an index always dealt to `(keptSize - 1) % playerCount`, which is **always the last seat**. So whenever the swap fired, the opening lead was handed deterministically to the highest-seated player instead of being left to the shuffle, replacing one fairness complaint with another in the single part of the deal that is meant to be random. Dealing everything removes the truncation, the mutable working copy of the deck and the scan-and-swap block together, and makes `Hands.openingLeaderSeat()` total by construction: the lowest Tampering card is in the deck, therefore it is in somebody's hand. `NoTamperingCardDealtException` is kept, but its only reachable meaning is now a deck containing no Tampering card at all — a deck-composition fault rather than a dealing outcome. No change was needed to make short final tricks work, because EOP-72 never removed that capability, it only stopped exercising it: `Trick.isComplete(Collection<Integer>)` and `Trick.seatToPlay(Collection<Integer>)` are both *told* which seats still hold cards and `PlayCardUseCase` passes that set, so a trick completes once every seat that still holds a card has played and an exhausted seat is never waited on. That behaviour is now pinned directly by `TrickTest.shouldCompleteAShortFinalTrick`, which also asserts the same trick reads as *incomplete* if an exhausted seat is wrongly reported as holding a card, rather than being left to be inferred from a full-game integration test. The regression guard for the deal itself is `HandsTest.shouldDiscardNothingAtAnyTableSize`, a parameterised test asserting **conservation** — that the dealt cards are exactly the deck — at 3, 4, 5 and 6 players, because a discarding deal satisfies every hand-size assertion while quietly losing cards. Restoring the truncation by hand fails it at 3, 5 and 6 players and, correctly, not at 4, where 68 divides evenly and nothing would have been discarded either way; that mutation was run and the guard confirmed to discriminate. This also resolves divergence 1 of EOP-83: `docs/api/openapi.yml` had documented the full deal all along, so the specification was right and the implementation was wrong, and the reconciliation is in favour of the specification. Two figures in the spec were corrected in passing — its five- and six-player hand lists were written ascending (`13/13/14/14/14`, `11/11/11/12/12/12`), contradicting both its own prose that the remainder goes to the lowest seats and its own three-player example of `23/23/22`. EOP-83's second divergence, the leaderboard `409`, is unrelated and remains open. The ADR-023 index row in `docs/adr/README.md` is also corrected: it still described the whole-deck deal throughout the EOP-72 period, so for one story it documented a rule the code did not implement. The architecture review of this change rejected it twice over on the Documentation Gate, and both findings are worth recording because neither was a code defect. The ADR index row for ADR-023 had been edited by pasting ~6.4 KB of its own prose *past* the row's terminating pipe, giving a four-column table a five-cell row; GitHub-Flavoured Markdown silently discards cells beyond the header count, so that text vanished from the rendered index while sitting in the source, and the row that vanished was the one this story exists to correct. `AdrIndexConsistencyTest` gains a fifth invariant, `shouldGiveEveryRowTheDeclaredColumnCount`, which counts cells the way a renderer counts them (GFM treats the outer pipes as optional delimiters, so they are stripped before splitting) and fails the build on any row that disagrees with the header — verified by reintroducing the surplus cell, which fails exactly that one test of the five and tolerates ADR-028's legal missing trailing pipe. Second, ADR-042 still asserted that the runtime deals 66 cards, which is the record of EOP-83 divergence 1; leaving it would have left two ADRs disagreeing about the current code, so it now carries a dated part-supersession noting the divergence closed **in favour of the spec** — the contract had documented the full deal all along and the implementation was what drifted. Three further precision fixes: the currency markers on `C4-Diagrams.md` and `runtime-view.md` advance to EOP-92 (C4's `POST /deal` row was itself stale for the whole EOP-72 period and nobody amended it); the claim that the short-final-trick rule is 'doing real work again' is qualified to 3, 5 and 6 players, since 68 divides evenly by four; and ADR-023 now states explicitly what the change does **not** claim — removing the swap makes the opening lead shuffle-determined, not uniform, each seat's probability being proportional to its hand size (0.338/0.338/0.324 at three players), exactly uniform only at four. That last note exists because the security review flagged the over-claim before any document made it, and there is still no automated guard that the opening leader is not a fixed seat.

- **Leaderboard never shown and all clients ejected to home when a game completed (EOP-82).** Two independent faults compounded. First, `eop.features.game-over` was still `false` in `src/main/resources/application.yml`, so `GameOverController` was never registered as a bean and `GET /api/v1/sessions/{sessionId}/leaderboard` fell through to Spring's static-resource handler, returning a *framework* 404 (`{"detail":"No static resource api/v1/sessions/.../leaderboard."}`) rather than an `application/problem+json` body. `PersistGameResultUseCase` is gated on the same flag, so no `game_result` row was ever written either — games played under a flag-off build have no result to display even after the flag is enabled. The flag is now `true` (EOP-82, 2026-08-18), completing the rollout begun in EOP-65. Second, and independently, `GameOverScreen.loadLeaderboard` treated a leaderboard 404 as a dead session and called `onSessionEnd()`, which clears `sessionStorage` and navigates to `home` — so a transient, recoverable "result not persisted yet" condition destroyed the session for *every* connected client simultaneously. The handler now ejects only on **403** (token invalid or expired); on 404 or 409 it renders the error message plus a `Retry loading results` button, so the screen degrades gracefully. Both faults had to be fixed: the flag alone would have left the frontend one failed persist away from the same ejection, and the frontend guard alone would have left the endpoint unmapped. Verified end-to-end against the local Docker stack by driving a full three-player game through the real API to `COMPLETED` (66 plays) and confirming `GET /leaderboard` returns 200 with all three players ranked and their `capturedBySuit` breakdown across the six STRIDE suits. Note that diagnosis was initially misdirected by rebuilding only `eop-ui:local`: the backend image was stale, and `./scripts/update-local.sh` (EOP-76) rebuilds **both** images — it is the only supported refresh path. This is the third defect in that class after EOP-76 and EOP-78. Both faults are now guarded by regression tests, because neither was catchable by the previous suite: `ShippedFeatureFlagDefaultsTest` reads `application.yml` off the classpath with `YamlPropertiesFactoryBean` and asserts the shipped default of all three feature flags, since `src/test/resources/application.properties` pins them all `true` and so any assertion via the Spring `Environment` would have passed against the broken YAML — the same masking trap EOP-27 removed for `spring.h2.console.enabled`; a new `Rfc9457ContractGuards` group in `GameOverControllerIntegrationTest` asserts the leaderboard 404 and 409 carry `application/problem+json` and, decisively, that the 404 detail does **not** contain `No static resource`, since a test asserting only `status == 404` passes in both the broken and fixed worlds; and `GameOverScreen.test.tsx` (the component previously had no test file at all — the only one in `ui/src/components/` without one, which is why fault 2 shipped) adds 8 tests, six of them covering the branches of the leaderboard error handler (a 404 does not eject; a 404 renders the error plus the retry button; clicking retry refetches and renders the leaderboard; a 403 still does eject; a 409 does not eject; and the happy path renders the rows with no retry button) plus two covering the facilitator-only `Start new game` button. The retry button holds a React pending state that disables it while a fetch is in flight, so a double-click cannot issue two concurrent requests against a route that has no rate limit (EOP-88); a visually-hidden `role="status"` region announces the retry, because disabling the button drops focus and the existing `Loading results…` region does not render on the error branch. It also carries `data-module="govuk-button"` to match its siblings, though that attribute is inert here — `main.tsx` imports only the compiled Design System stylesheet and never calls `initAll`, so no GOV.UK JavaScript is running and the double-click protection is entirely the React state's doing.

- **Drag-and-drop card play did not submit — the card snapped back to the hand (EOP-79).** `CardFace` renders the card artwork in an `<img>`, and an `<img>` is implicitly `draggable="true"` in every browser. Pressing on the card art and moving therefore started a *native* HTML5 drag, which fires `dragstart` and aborts the in-flight pointer stream with `pointercancel`. `handlePointerCancel` correctly treats that as "drag abandoned" and clears `dragState` without any drop-zone check, so `pointerup` never reached `handlePointerUp` and no play was ever submitted — the card simply returned to the hand. Neither `userSelect: 'none'` nor `touchAction: 'none'` on the wrapper suppresses native image dragging. Fixed by adding `draggable={false}` and `WebkitUserDrag: 'none'` to **all three** card `<img>` elements — the hand card in `CardFace`, the played card in the trick zone, and the drag ghost — plus `e.preventDefault()` in `handlePointerDown` as the equivalent guard for the text-fallback card face. The first two need it: `handlePointerCancel` filters no `pointerId` and is bound on the container the trick zone sits inside, so a native drag begun on a played card would abort a hand-card drag in flight. The ghost does not strictly need it, since its wrapper carries `pointerEvents: 'none'` and it can never be a press target, but it is guarded so the invariant holds uniformly and a future edit granting the ghost pointer events cannot silently reintroduce the bug. The server, the API layer, the drop-zone ref and the bounds arithmetic were all verified correct and unchanged. The bug escaped because the entire pointer-drag path had **zero** test coverage; `GameScreen.test.tsx` gains a `drag and drop card play` block (4 tests, suite 154 → 158), and `ui/src/setupTests.ts` gains a `typeof`-guarded jsdom shim for `PointerEvent` (a `MouseEvent` subclass, so `clientX`/`clientY` survive) and for `Element.setPointerCapture`/`releasePointerCapture`/`hasPointerCapture`, none of which jsdom implements. Note that only the two `draggable="false"` assertions guard this regression: jsdom cannot perform a native HTML5 drag, so the pointer-gesture tests are a coverage improvement for the hit-test path rather than a reproduction of the reported symptom. ADR-038 Consequences has been amended with three dated paragraphs recording the new invariant that no descendant of a drag surface may be natively draggable, the focus consequence of cancelling the `pointerdown` default action, and the accepted browser-level testing gap.

- Trick-taking rules as pure domain types: `Hand`, `Hands`, `Trick` and `TrickPlay` under `org.maglez.eop.entity`, with zero framework imports, carrying the whole rule set the game turns on — dealing, following suit, turn order, and who takes the trick (EOP-14, ADR-023). Four decisions are worth naming. **The opening lead is derived, never written down:** the seat holding the lowest-ranked Tampering card *actually dealt* leads, because the 74-card deck starts on the three of Tampering — a literal `3` anywhere in this code would be a defect against any future deck variant that starts differently, so `Hands.openingLeaderSeat()` computes it and `NoTamperingCardDealtException` covers the one case the rule cannot answer rather than falling back to an arbitrary leader. **Every card is dealt**, with the remainder going to the lowest seats, so at 74 cards all four supported table sizes (3, 4, 5 and 6 players) produce unequal hands and a short final trick; setting the remainder aside instead would have been tidier but can orphan the card the opening-lead rule needs, turning a derived rule into a hidden fallback reached only at certain player counts. That in turn makes a trick *one card from each seat that still holds cards* rather than a fixed count, so turn order is "the next seat clockwise still holding a card" and not the leader's seat plus the number of cards played — the simpler formula is correct for every trick except the last one at every player count, which is why ADR-019 now carries a dated amendment where an implementer would otherwise copy it. **A card played with no threat linked is a legal, ordinary play:** it still competes for the trick and simply scores nothing, so `TrickPlay.threatLinked` is a fact about a play and not an error, and a linked threat naming no component is accepted too — a facilitation tool that refuses a play in a live session because a text box is empty gets in the way of the conversation it exists to support. **A card named in a request is resolved out of the hand before any rule is applied to it,** and there is one guarded way in: `Trick.acceptPlay` checks the turn, resolves the card, checks follow-suit against the *resolved* suit and appends the play, with `Trick.play` reduced to package-private so nothing outside the domain can reach the unguarded mutator. A card is named by identifier, so its suit and rank travel as the caller's *claim*; checking possession by identifier and then reading the suit off the submitted object let a holder of the two of Tampering submit that identifier labelled ace of Elevation of Privilege, pass possession, escape follow-suit because the claimed suit was trump, and take the trick with a card that was never dealt. Three public checks a caller was merely *documented* to call in the right order were two optional guards in front of an open mutator, not defence in depth. **The acting seat is a parameter in its own right and is never read from the payload:** `acceptPlay(int actingSeat, TrickPlay candidate, Hands hands)` takes the seat the caller has authenticated, refuses the play with `NotYourSeatException` if it describes a different seat, and then *derives* both the hand and the set of seats still holding cards from `hands` rather than accepting either. An earlier revision took the seat from the submitted play and cross-checked only the hand against the player, which is a two-way check on a three-way fact — seat, hand and player — and `Hand` deliberately carries no seat number, so the binding could not be made from those arguments at all. Because the session state already publishes every player's identifier *and* seat to every other player, a player really sitting at seat 2 could submit its own identifier with someone else's seat number and its own hand: the play was accepted out of turn, the victim's seat was marked as having played so they were locked out of the trick for good, and the attacker could then play a second card from the same hand at its real seat and take the trick. The player identifier remains the one caller-supplied claim, and it is checked against the seat's occupant rather than believed. **The seat is settled before anything else is looked at** — whether it is a seat at this table at all, whether the play claims that seat, and whether the player the play names is the one occupying it — because all three are answered entirely from facts the requester already sent, so a refusal discloses nothing it did not already know. A play naming a seat's non-occupant is refused with `PlayerMismatchException`, its own type rather than a bare `IllegalArgumentException`, so the boundary can tell impersonation from a malformed argument without matching on message text and can carry both player identifiers as fields instead of interpolating them into a message a caller reads. Turn order comes next, before the card is looked at, so a player who is not to play learns nothing about their own cards from the refusal, and `Trick.nextLeaderSeat(seatsHoldingCards)` passes the lead on when the winner has run out of cards — a winner's seat handed back unconditionally would open a trick nobody could play into, which is reachable at every player count and would have stopped the game with no exception to log. Free text a player types is bounded and refused if it carries control characters or bidirectional overrides, because a NUL byte cannot be stored in a PostgreSQL `text` column, CR and LF in text that reaches a log let a player forge log lines, and a bidi override lets a component name display differently from the one stored. On rendering: `Hand`, `Hands` and `TrickPlay` print only counts, because knowing an opponent's cards is knowing what they can and cannot follow with, and the default rendering would leak a hand — or a player's notes — into any log line that interpolated it. `Card.toString` drops its threat prompt as bulk rather than as a secret; the deck is published, so what is confidential is the *association* between a player and an unplayed card, and that guarantee lives in the redacted containers and in `Hand.cards()` being documented as confidential rather than in `Card` itself. A `Trick` also refuses, at construction, a play list in which one player holds two seats or two plays share an identifier, and refuses plays that do not run clockwise from the leading seat — the first of those is the stored form of the seat-impersonation defect above, and all three are checks a trick can make from the plays alone. What it cannot check is follow-suit, because that is a question about a hand and a trick holds no hands, so `Trick.reconstitute` is documented as **not** a validating gate for the rules of play and Slice B's persistence adapter must be trusted to store only what `acceptPlay` produced. `Hands.deal` refuses two seat assignments sharing a seat order, which previously collapsed silently on insertion and left one seat holding two round-robin shares of the deck. `docs/requirements/PRD-eop-card-game.md` §3.3 now carries dated deviation notes against the two sentences the implemented rules depart from — "one time around the table" and "the winner of a trick leads the next trick" — each linking ADR-023, because both are the shipped instruction card's wording and both are right for a game in which every hand empties together. All six of the story's domain refusals are now mapped to problem details and unit-tested, as the error-handling rules require of every known exception: a play claiming a seat its requester does not occupy and a play naming a player who does not hold that seat are both **403**, being impersonation rather than malformed input; a play out of turn is **409**; a play that breaks follow-suit, or names a card the hand does not hold, is **422**, because every field parsed and the refusal came from a rule of the game. Two of those mappings deliberately do not echo the exception's message: the card refusal reports only the card identifier and not the identifier of the hand, and the player-mismatch refusal returns a fixed sentence, its message having been reduced to name a seat and nothing else so that logging it cannot leak either player. A deck with no Tampering card is the one **500** here, because the deck is seeded reference data and every valid deck contains the suit. Nothing is wired up yet — no schema, no endpoint, no dealing on session start — and scoring is EOP-15
- Storage for the trick-taking domain: migration `004-trick-play-schema.xml` creates `hand`, `hand_card`, `trick`, `trick_play` and `trick_play_component`, and adds `game_session.current_leader_seat` (EOP-14, ADR-023). It also adds `uq_player_id_seat` to `player`, a table it does not create. The schema lands before the JPA entities and adapters deliberately, because `ddl-auto: validate` fails startup on an entity with no matching table. Six decisions are worth naming. **`trick_play.components` becomes a child table with an explicit `ordinal`, and the 20-element cap is enforced three times over** — once in the domain constructor, once in storage as `PRIMARY KEY (trick_play_id, ordinal)` plus `CHECK (ordinal >= 0 AND ordinal <= 19)`, and once at the boundary in the slice that adds the request DTO. That is defence in depth rather than duplication: the domain stops bad input, the constraints stop a bad write from a future adapter bug or a hand-run statement. `(trick_play_id, component_name)` is deliberately *not* unique, because the domain accepts repeated component names and a stricter constraint would turn a legal play into a 500. **`hand_card` gets no ordinal**, which looks inconsistent next to the components table until you notice that `Hand` sorts its cards in its own constructor so that two hands holding the same cards compare equal whichever order they arrived in — dealing order carries no meaning, whereas the order a facilitator typed their component names in does, so one is canonicalised and the other preserved as typed. **`trick` gets no `led_suit` column**, because `Trick.ledSuit()` derives it from the first play and a stored copy would be a second authority no write path populates. **The three `trick_play` unique constraints carry the invariants through a reload**, so they survive rather than living only in whichever entity happened to be in memory — but only one of them is the stored form of a Slice A security defect. `(trick_id, card_id)` closes card forgery within a trick. `(trick_id, player_id)` stops one player occupying two seats in a trick, which is a *different* exploit from the seat impersonation Slice A had to fix twice, and an earlier draft of this entry claimed otherwise. **Seat impersonation is closed instead by binding a stored seat to the seat its player actually holds:** `uq_player_id_seat` on `player (id, seat_order)` gives a composite foreign key something to reference, and `fk_hand_player_seat` and `fk_trick_play_player_seat` then make a hand or a play at a seat its player does not hold structurally unrepresentable, rather than merely unlikely. That reverses a deferral taken earlier the same day: the seat and cross-session protections were argued as one problem and a sound objection to the expensive half — denormalising `game_session_id`, a copy that can disagree with its parent — was allowed to carry the cheap half with it, when in fact `seat_order` was already on both tables and the binding needed one unique constraint that adds no invariant of its own. The single-column keys to `player(id)` are subsumed by the composite ones rather than omitted, and that subsumption holds only while both key columns stay `NOT NULL`. **What is deliberately still not enforced is session scoping**, and the honest consequence is that the composite key proves a player holds that seat *somewhere*, not that they are at this trick's table — seats are numbered from zero in every session, so a player at seat 2 in another session still satisfies it and can still take this session's seat-2 occupant out of play. Narrowed to cross-session attackers, then, not closed; it is owned by Slice C's play use case, which resolves the acting player from the identity token, and ADR-023 records both the reversal and what remains. **Foreign keys were missing on `trick_play.card_id` and `trick.winner_play_id`** and are now present; an unconstrained `card_id` in particular left card forgery re-openable one layer below the code that had just been hardened against it. `fk_trick_winner_play` is `ON DELETE SET NULL` rather than the `NO ACTION` first written, because measurement showed NO ACTION made a resolved trick undeletable outright — at the cost that deleting a winning play directly now silently unresolves its trick, which nothing but a comment currently prevents a later slice from doing. The concurrency test ADR-023 places in this slice rather than a later one — before the constraint exists there is nothing to assert against — drives one player racing itself through separate JDBC connections, which is the ordinary double-tap a real client produces; a second, sequential test uses two players from different sessions who both legitimately hold the same seat number, because that is the only construction left in which `uq_trick_play_trick_seat` is the sole constraint that can fire, and it doubles as the recorded proof of the cross-session gap above
- Range bounds on every seat and sequence column: migration `005-seat-and-sequence-bounds.xml` adds `chk_player_seat_order`, `chk_trick_sequence` and `chk_game_session_current_leader_seat` (EOP-14, ADR-023). This closes a gap found by measurement rather than by reading: against the merged Slice B schema, `player.seat_order = -7`, `trick.sequence = -5` and `game_session.current_leader_seat = 9999` were all *accepted* by the engine, while the domain refuses all three. Three points are worth naming. **One CHECK on `player.seat_order` bounds three tables**, because `fk_hand_player_seat` and `fk_trick_play_player_seat` bind `hand` and `trick_play` to `player (id, seat_order)` — so the seat range on the child tables is inherited, and the composite keys that carry it prove consistency with the parent but never validity, which is exactly why the parent needed a bound of its own. **`trick.sequence` gets a lower bound only**, because no upper bound is derivable — a three-player deal runs to `ceil(68 / 3)` = 23 tricks and no domain constant caps it — so `>= 1` is the whole of what is known and inventing a ceiling would reject legal play. **The bounds are pinned to `GameSession.MAXIMUM_PLAYERS` by a test that reads the changeset XML**, since Liquibase cannot read a Java constant and the literal `5` is a hand-copied counterpart: raising the player cap without editing the migration would leave storage stricter than the domain and turn a legal join into a 500. Each constraint is tested in both directions, because a test that only proves rejection would pass just as well against a CHECK that rejected every value, legal ones included. Adding a constraint to `player` from a later changelog file rather than editing `003` is the only lawful option — merged changesets are immutable (ADR-008) — and follows the precedent `004` set when it added `uq_player_id_seat` to the same table. Writing all three as raw `<sql>` is likewise forced: `addCheckConstraint` is a Liquibase Pro change type and is absent from the open-source `liquibase-core` this project depends on. Landing `005` also exposed a latent defect in Slice B's own round-trip test, which rolled back a hard-coded nine changesets to undo `004` — correct only while `004` was the last changelog file, since Liquibase counts backwards from the last change *applied*. - An error vocabulary for trick play: seven domain exception types and their problem-detail mappings — `PlayerNotInSessionException` (404), `HandAlreadyDealtException`, `HandNotDealtException`, `TrickAlreadyOpenException`, `AlreadyPlayedInTrickException` and `CardAlreadyPlayedException` (409), and `WinningPlayNotInTrickException` (422) — landing ahead of the use cases that will throw them (EOP-14, ADR-023). Five decisions are worth naming. **A caller who is not in the session is answered exactly as a session that does not exist**, byte for byte and not merely with the same status: a 403 would confirm to a stranger holding a guessed or leaked identifier that it guessed correctly, and two 404s with different titles would be as good an oracle as a 403, so the test asserts equality of the two whole `ProblemDetail` bodies. The parity is held in place by the exception itself, which builds the same message as `SessionNotFoundException` for the same identifier and carries the session id **and nothing else** — a field naming the player, the seat or the reason would eventually be logged into a response, and a field that does not exist cannot be. This follows the fixed-body reasoning already written for an unknown join code, with the one deliberate difference that a join code is blanked because roughly thirty bits are guessable while a caller-supplied session identifier can be echoed back safely. **The candour argument that licenses naming a missing session is now scoped in the code that makes it**: the Javadoc on `SessionNotFoundException` and its handler argued from a 122-bit identifier, which is sound about whether a session exists and says nothing about who may see it, so both now cross-reference the membership answer rather than leaving the next reader to generalise a correct argument past its premise. **A winner from another trick is 422 and not 409**, because a conflict entitles the caller to retry once the state moves on and no state this application can reach makes a play from one trick the winner of another; it is also logged at warning level with both identifiers and returns neither, since ADR-023 records that this check will never have a storage constraint behind it — the composite key that would provide one collides with the rule that lets a winning play be deleted — so the log line is the only evidence that will ever exist. **The two conflicts on a trick are kept apart**: one refuses a second play from a seat, the other one card appearing twice whichever seat played it, and a test pins the titles as unequal so that collapsing them into a single "conflict" cannot pass. **The two states of the deal are kept apart on the same reasoning, and naming the second of them is what took a seventh type**: `HandNotDealtException` is the mirror of `HandAlreadyDealtException`, the two being opposite states of one column — `game_session.current_leader_seat` — and a vocabulary naming only one of them forces the other to be reported as something it is not. Before it existed, that branch of `TrickPlayRepositoryAdapter.sessionMoved` answered `SessionNotJoinableException` carrying `IN_PROGRESS`: the right status with an explanation that contradicted itself, telling a caller a session was not joinable while handing back the status saying it was in progress. @architecture-guardian found it in this slice's architecture review, and the fix was a type that can name the state rather than a different status code — the branch is reached by asking to open the first trick before the deal, which is an ordinary caller mistake rather than a broken invariant, hence a 409 and not a 500. The two 409 titles are deliberately unequal, and a test pins that they do not collapse into each other, because both are conflicts on one column and the title is the only thing saying which way it went. The translation table in ADR-023 was also one row short and is amended here: `uq_trick_session_sequence` is reachable by two requests racing to open the same trick, and without a name for it that race answered 500. What C1 cannot yet test is the status over the wire, because it adds no route — the handlers are proved as pure functions here, exactly as the existing mappings are, and the wire-level assertions arrive with the endpoints
- Persistence mappings for the trick-play tables: JPA entities for `hand`, `hand_card`, `trick`, `trick_play` and `trick_play_component`, plus the `current_leader_seat` column on the session entity (EOP-14, ADR-023). The point of the commit is not the eight new classes but what mapping them switches on. `spring.jpa.hibernate.ddl-auto` is `validate`, and until now that setting was nearly free: three tables were mapped, the five created by Slice B were not, and Hibernate validated nothing about them — so a mapping could disagree with the migrations indefinitely and only a query that happened to touch the wrong column would ever say so. Mapping them means every column and type on all eight tables is now checked at every context start, on H2 in the suite and on PostgreSQL in production. Because that check is silent when it passes, it gets a test of its own rather than being left as something the other integration tests catch by accident: `MappedSchemaValidationIntegrationTest` asserts the effective `ddl-auto` value, so switching it to `none` fails loudly instead of quietly removing a guard, and then issues a real bounded `SELECT` of every mapped column of every entity, which is a stronger check than startup validation and one that names the entity when it breaks. The test was confirmed non-vacuous by measurement — renaming a single mapped column to `seat_ordering` turned all nine cases red — because a schema test that cannot fail is worse than none. Three mapping decisions carry reasoning. **No collection mappings anywhere**, following the session entity's existing refusal of `@OneToMany`: a played card is one delete and a play is one insert, and a cascade or orphan-removal mapping would turn each into a diff of two collections, which matters here more than it did for seats because the statement issued has to be exactly the statement it looks like — the row lock taken before it is the concurrency guard. **The two link tables use `@IdClass` rather than `@EmbeddedId`**, since both have a composite primary key that genuinely is their identity and no surrogate to invent; `@IdClass` keeps the key columns as ordinary fields, so a query reads `deleteByHandIdAndCardId` instead of routing every predicate through an embedded object. **`current_leader_seat` is mapped on the row and deliberately nowhere else** — the domain `GameSession` gains nothing, because the current leader is a fact about the trick in progress and `Trick` already derives whose turn it is from its own plays, so a copy on the aggregate would be a second authority on it. It is stored because it is the compare-and-set witness the conditional writes name, it is `Integer` rather than `int` because null is meaningful and is how "no cards dealt yet" is stored, and it advances once per trick rather than once per play. A play reads it and takes the row lock without changing it
- Storage for dealt hands and played tricks: the `HandRepository` and `TrickRepository` ports, five Spring Data interfaces, one `TrickPlayRepositoryAdapter` implementing both, and three further conditional updates on the session row — `claimDeal`, `touchWhileLeaderSeatIs` and `advanceLeaderSeat` (EOP-14, ADR-020, ADR-023, ADR-024). Five decisions carry the design and govern the first half of this entry; what follows them records what shipped, and the argument that used to fill the rest now lives in an ADR of its own. **There is no `save`**: each write is narrow and conditional on the state the caller observed, because a blanket save would have to diff an immutable aggregate against storage to learn which rows to write and could not be conditional on anything — which is precisely the compare-and-set turn order depends on. **Both ports are implemented by one class**, because playing a card deletes a `hand_card` row and inserts a play and its components and those must commit together; the two decompositions that keep one adapter per port either admit that torn state or put `@Transactional` in the use-case package. *(Retracted — see ADR-024's amendment and the next entry: those are not the only two decompositions. A `@Transactional` method in the outer ring composes two adapters through the `REQUIRED` propagation they already carry, with no import inside `usecase`. One class per aggregate survives on ownership grounds, not on a false dichotomy.)* **Every write begins with a conditional update on the session row**, which is both the compare-and-set whose zero-rows answer means the world moved and the row lock taken in the order the ADR requires (session, then hands, then tricks). Zero rows is never success and never a server fault: one helper spends a single extra read on the already-failing path to answer that the session is missing, is not in progress, has already been dealt, has not been dealt at all, or that the caller's leader-seat snapshot is stale — the last being an out-of-turn play, since the leader seat is the value turn order is computed from, and a double resolution lands there too because the first resolution moved the seat. **Hands are read whole or not at all**, since `Hands.reconstitute` re-runs a cross-seat invariant no database constraint stands behind and a per-seat read would satisfy it vacuously, switching off its only enforcement; writes stay a one-seat delta. Plays are ordered by rotation from the trick's leader seat rather than by `played_at`, because the domain reads the led suit from the first play and a timestamp can tie. **The seat foreign keys are a backstop rather than the check**: the adapter reads the session's seats before inserting and refuses a wrong seat itself with 403, or an unknown player with the same 404 a missing session returns, and a key that fires anyway is logged at warning level with its constraint name and rethrown as a server fault, because it means a check above it was missed. Checking first is sound only because a seat never moves once seated — the column is mapped non-updatable — so unlike seat *allocation* there is no window to narrow. Each index maps to one exception, proved by driving the adapter through a live schema rather than a stub: `uq_hand_session_seat` becomes `HandAlreadyDealtException`, `uq_trick_session_sequence` `TrickAlreadyOpenException`, `uq_trick_play_trick_seat` and `uq_trick_play_trick_player` both `AlreadyPlayedInTrickException` — one player makes one play whichever index catches the second — and `uq_trick_play_trick_card` `CardAlreadyPlayedException`. Three details of that test are load-bearing: cards come from the seeded catalogue, because the domain's deck fixture mints synthetic identifiers `fk_hand_card_card` refuses; the class is not `@Transactional` and cleans nothing up, since the first violation marks a test-managed transaction rollback-only and would poison every later assertion, so each case mints its own identifiers and commits as production does; and two indexes must be reached deliberately, `uq_hand_session_seat` by nulling the leader seat *and* dealing fresh hand identifiers, because reusing them makes `saveAndFlush` merge and silently succeed, and `uq_trick_play_trick_card` by inserting a `hand_card` row by hand, since the adapter's own delete refuses the second play first. The negative controls are that a deal naming an unseated player, and one naming a seated player at somebody else's seat, each write *nothing*; and what the test cannot reach is recorded in it — the missing-card server fault, while the foreign keys make a referenced card undeletable, and both seat backstops, because the adapter refuses first, so a fired backstop's warning line is untested by construction. Two reads also turn out to throw `InvalidDataAccessApiUsageException` and not the JPA-specification `IllegalStateException` they appear to, because the adapter is a `@Repository` and Spring translates on the way out; both still fall to the catch-all 500, and the assertions pin that, since an `IllegalArgumentException` would render as a 400 and blame the caller for a fault of ours. Reading the leader seat revalidates the column against the domain's seat count, and a seat bound for a column is refused at the boundary rather than left to the CHECK; both guards are pinned as the pure functions they are, the read guard because it cannot be reached end to end at all — this slice's range constraint refuses the very row the guard exists to survive — and the write guard because only its negative limb is out of reach. The three range constraints carry preconditions that halt with the query to run instead of an engine error naming neither the row nor the reason. A security review rejected the slice for documentation claiming an authorisation this layer does not perform: it authorises nobody, none of its statements takes a player identifier, and the seat check is a check on the *row* rather than on the requester. [ADR-024](docs/adr/ADR-024-trick-play-persistence-boundary.md) now carries that decision, the argument behind it, and the obligation it puts on Slice C2 — authorise the requester first, in every use case, because no test here fails if you do not. This slice's documentation work landed with it: ADR-024 was created, and ADR-023, ADR-020, ADR-013, `docs/adr/README.md`, `docs/architecture/C4-Diagrams.md` and `docs/architecture/runtime-view.md` were corrected, because mapping the five tables falsified standing claims in three documents that the tables were unreachable — the containment is now the absence of a use case and a route rather than the absence of a mapping
- The use cases that drive trick play: `DealHandsUseCase`, `PlayCardUseCase` and `ResolveTrickUseCase`, plus the `DeckShuffler` port and its `SecureRandomDeckShuffler` implementation, a third `findWholeDeck()` method on `CardRepository`, and two new domain exceptions with their 409 mappings — all three use cases wired in `UseCaseConfiguration` behind `eop.features.trick-play`, off by default (EOP-14, ADR-025). Slice C1 shipped ports that could reach five trick-play tables and no bean that did; this is the slice that adds the beans, which is why the flag is a merge precondition rather than a nicety, and `TrickPlayDisabledIntegrationTest` asserts all three beans are *absent* with the flag off rather than asserting 404s, because a route does not exist yet and asserting absence pins the mechanism instead of a symptom. Nine decisions are worth naming. **Dealing is its own use case rather than a step in starting a session**, and this is a chosen seam rather than a forced one — an earlier version of this entry and of ADR-025 claimed it was forced, and an architecture review refuted the claim. What is true is that `recordDeal`'s conditional update requires the status transition to have been *written* first, not committed, because a transaction reads its own writes; and that the use-case layer may not demarcate a transaction itself, since that would need `org.springframework.transaction` in a layer required to have no Spring import at all. What does not follow is impossibility: a `@Transactional` method in the outer ring calling start and then deal joins both adapter writes into one transaction through the `REQUIRED` propagation they already carry, with no import added to `usecase`, which is where Clean Architecture puts demarcation anyway. That composer is declined on cost, and the cost is nothing to do with imports — `StartSessionUseCase` publishes `GAME_STARTED` over SSE during its own execution, so a composed transaction broadcasts a start that a rolled-back deal then unmakes, trading a recoverable inconsistency for an unrecoverable one; making it safe needs publish-after-commit, which is a larger design than the window it removes and belongs in its own ADR. The started-but-undealt window that leaves is accepted and recoverable, because `recordDeal` writes the leader seat only where none is recorded, so a retry is free and idempotent — recognising that state is the route slice's work, and ADR-025 records the alternative of one start-and-deal endpoint as deferred rather than rejected, which stays available precisely *because* the deal is its own class. **Authorising the requester is the first port call of all three**, since the ports take no acting player and say so: beneath them a conditional update that matches no rows re-reads the session and answers one of five distinguishable states, which is the right candour for a member and an oracle for a stranger, so each use case has a test asserting a stranger is refused **before any hand is read** — the assertion is on the repository double's read log, because a refusal that has already read is a refusal that has already leaked timing. **`PlayCardCommand` carries no seat, no player identifier, no suit and no rank.** Each is derivable from something the caller cannot choose — seat and player from the identity token, suit and rank from the deck row — and the two defects a security review found in Slice A were exactly a caller-supplied seat and caller-supplied suit and rank, so they are now inexpressible rather than validated, which is a stronger guarantee than a rule somebody has to remember to write. **No use case pre-checks a state its conditional write already arbitrates**: a status or already-dealt check would read state, let go of it, then write, which is an illusion of safety and duplicates ADR-020's compare-and-set — the defence in depth that is real here is *the use case authorises identity, the port enforces state atomically*, two different questions rather than one asked twice. **Two pre-flight guards exist only to order a refusal before a commit**, and neither is an authority: `hand.resolve(card)` and a leader-seat comparison run before `openTrick`, because `openTrick` commits a trick row and `Trick.acceptPlay` would refuse *afterwards*, leaving an open, empty trick nobody asked for and no later slice knows how to clear. At the end of a hand every hand is empty, so without the first guard a caller would receive an `IllegalStateException` — a 500 — for what is properly a 422. `Trick.acceptPlay` still re-checks both and still owns the answer. **The deal returns `void`**, because a result carrying every hand is precisely the shape that leaks private information — the reason `Hands.toString()` names no card — and a facilitator has no more right to see the table's cards than anyone else; a player reads their own hand through a query of its own in a later slice. **Only the facilitator may deal, but any seated member may resolve a trick**, because resolution is a mechanical consequence of the last card and gating it on one person would stall a table whose facilitator's connection dropped. **None of the three broadcasts anything, which makes them the first writes in the system that change what every player can see and tell nobody.** No use case here takes a `SessionEventPublisher`, and no `SessionEventType` constant is added, deliberately: that constant carries the name appearing in the `event:` field of an SSE frame, the name is fixed by `docs/api/openapi.yml` under contract-first (ADR-004), and minting one in a slice that publishes no contract would only guarantee a rename when Slice D writes it. Until the broadcast is wired a client learns of a deal, a play or a resolution **only by re-reading**, so the stream stays silent for the whole of a trick — Slice D owned the wire names and Slice E passed the publisher in, so all three names are emitted as of that slice; nothing in the repository failed while it was missing, which is why it is a numbered decision in ADR-025 and not only a line in a handoff. **The pre-flight ordering above is an argument rather than a mechanism, and its scope is now written down**: it holds by exhaustion over the refusals `Trick.acceptPlay` has today, since on an opening play no suit has been led and the trick is empty, and the refusals that could still fire are each pre-flighted before the write. Any refusal added to `acceptPlay` — or to `Trick`'s constructor, which carries nine of its own — reopens the orphan-trick window silently, from a class that never mentions trick rows; the durable fix is to persist the trick and its first play in one call, which changes the `TrickRepository` contract. Two smaller things carry reasoning too: `NoTrickToResolveException` and `TrickNotCompleteException` are separate types answering 409, joining `HandNotDealtException` to make three too-early states with three titles, because a client that says "waiting for the deal" rather than "waiting for the lead" rather than "waiting for a player" cannot tell them apart from one shared answer, and all three are retryable; and the shuffle is a port rather than a `java.util.Random` parameter so the security-relevant choice of source is made once in an adapter and cannot be weakened by a caller passing a seeded generator, with `Hands.deal` staying deliberately pure so every use-case test above it gets a permutation it can predict. `ResolveTrickUseCase` also gives `WinningPlayNotInTrickException` the only thrower it will ever have — unreachable through `Trick.resolved()` today, written because `fk_trick_winner_play` confines a winning play to the `trick_play` table and nothing narrower, and the composite key that would confine it cannot be expressed in Liquibase. An enumeration of a race is a guess that passes until the machine is faster. - The state of play, the end of a hand and the trick-play broadcast: `GET /api/v1/sessions/{sessionId}/tricks/current` with `GetTrickStateUseCase`, the `TrickState` result and the `TrickStateDto` transport record, publishing `seatToPlay`, `complete`, `nextLeaderSeat` and `handComplete` (EOP-14, ADR-014, ADR-020, ADR-023, ADR-027, ADR-028). This is the read the flag could never have been turned on without: `TrickDto` deliberately answers none of those four questions, because all four depend on which seats still hold cards, which is not part of a trick, so before this slice no client could find out whose turn it was except by attempting a play and being refused. Its two seat answers come from different authorities — `seatToPlay` from the trick while one is open and otherwise from the seat the session row records as leading, `nextLeaderSeat` derived by the domain from the cards — and nothing reconciles them on the way out, because a disagreement between the row and the cards is a defect a client is entitled to notice rather than one the server should hide. The contract was committed alone and first, in `b39e6a7`, touching only `docs/api/openapi.yml`. `TrickRepository.recordResolution`'s next-leader parameter widened from `int` to `OptionalInt` so that a played-out hand records `current_leader_seat = NULL` rather than a winning seat with nothing left to lead — Slice C2 sent the winning seat there as a placeholder because the port had no value meaning nobody — with `advanceLeaderSeat`'s parameter boxed to `Integer` and no new changeset, because changeset `005`'s `chk_game_session_current_leader_seat` already permits NULL. That makes NULL carry two meanings, so `claimDeal`'s `current_leader_seat IS NULL` predicate is no longer the whole deal-once gate: for a played-out session the claim now succeeds and `uq_hand_session_seat` refuses the second deal one statement later, as the same `HandAlreadyDealtException` and the same 409, rolled back inside the same transaction so the caller cannot tell which check did the work (ADR-020 amended, twice). `HandCompleteException` is the third state of that column to earn a name, mapped to 409 with its own title `Hand complete` and guarded at the top of `PlayCardUseCase` through `Hands.allEmpty()`, which gains its first caller: without it a play into a spent hand was refused by `Hand.resolve` as a 422 saying the caller had named a card it did not hold, when the honest answer is that it holds no cards at all. The shared `sessionMoved` helper gained a sixth answer, telling a played-out hand from an undealt one by a new derived `existsByGameSessionId`; nothing in the product reaches that branch today, because for the last trick to have been resolvable every seat still holding a card had already played, and it is written anyway because the alternative is an unreachable branch that answers a lie. The three event names minted but never emitted in Slice D — `hand-dealt`, `card-played` and `trick-resolved` — are now published by `DealHandsUseCase`, `PlayCardUseCase` and `ResolveTrickUseCase`, each after its write returns so a refused operation announces nothing, each carrying a type, a session and an instant and nothing else so no hand and no play is disclosed to the table, and none of them guarded at the call site because `SessionEventPublisher` places the obligation not to fail a request on its implementation. Two things were decided not to do (ADR-028): `eop.features.trick-play` stays `false` on merge, so all five slices ship complete and unreleased and turning the flag on becomes its own story whose predecessors are ADR-026, EOP-48 and EOP-15; and the session does not move to `COMPLETED`, because that word is documented as a hand whose score is final and this story computes no score, so EOP-15 owns the transition and a client watching only `GET /api/v1/sessions/{sessionId}` still never sees a session finish. A duplicate off-position test written during this slice was deleted rather than kept: `TrickPlayDisabledIntegrationTest` already asserts the beans and the routes in one class on purpose, no off-position gap ever existed, and it gained two tests for the new bean and the new route instead of a sibling.
- The scoring rule as pure domain types: `ScoredPlay`, `Standing` and `ScoreSheet` under `org.maglez.eop.entity`, with zero framework imports, computing the score of a game from the tricks already played (EOP-15, ADR-030). No schema, no route and no use case ships with them — this is the rule on its own, provable without any of that, and `ScoreSheet.of(players, tricks)` is a pure function whose whole input is a seating and a list of tricks. Seven decisions are worth naming. **The score is derived and never accumulated.** There is no running total anywhere, no counter column and no increment on the play path, because a stored total is a second authority that can disagree with the plays that produced it, and the moment it does there is no way to tell which of the two is the game. Deriving it also settles what the ticket's "computed and stored server-side" is really protecting: the constraint is about *authority* — the client never asserts its own score — and a derivation satisfies that more completely than a stored figure a write path could get wrong. **The rule is one point for a threat connected to your own card plus one for taking the trick, and it must not be embellished.** The richer system the deck's author tried — four for a threat on your own card, three, two and one for threats on other people's, plus bonuses for face cards and aces — was abandoned because playtesters could not compute it at the table and looked to the facilitator at the end of every round to be told who had scored. That constraint does not bind a server, so a richer rule is cheap to add later and is recorded as an option; it is deliberately not built here, because shipping the simple rule first is what makes the digital form's advantage measurable rather than assumed. **A linked threat that names no component still scores.** `TrickPlay`'s Javadoc left this open for this story to settle, and it settles it in favour of scoring: the written rule keys on the threat being connected, not on a text box being filled; the application holds no model of the system under discussion (PRD §3.4) and therefore *cannot* validate a component name, so making a point conditional on one would make the score depend on unvalidated client free text, which is exactly what "a client must never assert its own score" forbids; and the printed Score Card's Component(s) column is legitimately blank on plenty of real rows. **The two points a row can earn stay separate rather than pre-summed.** `ScoredPlay` carries `threatPoint` and `trickPoint` as distinct booleans because the Score Card is read by humans mid-game who need to see *why* a row scored — a row scoring one point because the threat landed looks nothing like a row scoring one point because the card took the trick, and a single `points` field makes the two indistinguishable at exactly the moment somebody queries the total. A play with no threat linked that still takes the trick is an ordinary row, not an anomaly. **Ties are shown as ties and never broken.** Standings use competition ranking, so four players on 7, 5, 5 and 2 hold positions 1, 2, 2 and 4, and `Standing.tied` is published even though a caller could derive it, because the interesting fact about a shared position is that it is shared. There is no tie-break rule to get wrong later because none is invented now. **A display name is never a key.** `DisplayName` is free text, unverified and explicitly not unique — two people at the same table may choose the same name and the humans on the call disambiguate them — so every row and every standing keys on `playerId` and carries the name for rendering only. `pointsOf` takes a player identifier and refuses a stranger rather than answering zero, because zero is a legitimate score and silently returning it for somebody not in the game would be a plausible lie. **An unresolved trick contributes threat points but no trick point.** The trick list may end with a trick still on the table, and the sheet scores its plays' threats while awarding nobody the trick, which makes a running score monotone as play proceeds — a total can never fall — and means the same class serves the mid-game read and the final standings with no second code path. Deciding that the game has *ended* is not this class's job and it does not try: it reports the score of the tricks it was given, and the session owns the transition to `COMPLETED`
- Reading the score: `GET /api/v1/sessions/{sessionId}/score` answers any seated player with the Score Card's five columns — name, points, card, component(s) and notes on threat — one row per play and one standing per seat (EOP-15, ADR-031). The single new port method returns the session's whole trick history and filters nothing, so an unresolved trick still contributes its threat points and a running score stays monotone; its adapter batches four reads for the whole session instead of three per trick. There is deliberately no `409`: before the deal, everybody on nothing is a true answer rather than a missing one, which is why this read needs neither the hands nor a session status. ADR-027's prohibition on a collection of every player's state is answered rather than assumed — it protects *private* state, and a score names only cards already face up. Slice A's eight `IllegalArgumentException` refusals became a single `ScoreNotDerivableException` carrying a typed reason and mapped to 500 with a body indistinguishable from any other server fault, so a contradiction in the stored game can no longer be reported as the caller's mistake nor echo an identifier back to whoever guessed a session. The route ships behind `eop.features.trick-play`, still `false`, with the flag pair now pinning eight beans absent and six routes 404 in the off position and eight beans present in the on. Deciding that a game has *ended* remains the session's job and arrives with the third slice.

### Fixed

- **`handleSessionFull` and `handleSessionNotJoinable` were echoing internal identifiers in 409 responses (EOP-54, EOP-55).** Both handlers called `exception.getMessage()` to populate the RFC 9457 `detail` field. `SessionFullException` builds its message as `"Session <UUID> already seats the maximum of <capacity> players"` and `SessionNotJoinableException` as `"Session <UUID> is <SessionStatus> and does not accept that request"` — leaking a session UUID and internal state (capacity constant and lifecycle enum value respectively) to a caller who supplied only a join code and never held either. Both handlers now set a fixed literal detail string, following the precedent established by `handleUnknownJoinCode` and `handleSeatAlreadyTaken`. `handleSessionFull` is join-scoped and uses `"This session has no available seats. Try a different join code."`. `handleSessionNotJoinable` is also raised on start, deal, play and resolve paths, so its detail is path-agnostic: `"This session is no longer in the lobby."` — true for every caller and leaking neither the UUID nor the enum name. The diagnostic is preserved server-side at WARN level via `LOG.warn("Session state refused the request: {}", exception.getMessage())`. The no-disclosure guarantee in `docs/api/openapi.yml` is updated to cover all three 409s on the join-by-code endpoint and the start endpoint.

- **`SseSessionEventPublisher` had three resource-exhaustion defects (EOP-20, ADR-034).** First: `new SseEmitter(0L)` created emitters with no timeout, so a client that connected and never disconnected held a thread and a slot indefinitely — an unattended load test or a browser tab left open overnight would eventually exhaust the server's accept queue. Second: there was no cap on the number of concurrent SSE subscribers, per session or globally, so a caller could subscribe thousands of times and fill the in-memory registry. Third: the heartbeat ran all emitter sends inline on a single `sse-heartbeat` thread, so one slow reader blocked the entire sweep for every session. All three are now closed. **Emitter timeout:** `SseEmitter(0L)` is replaced by `SseEmitter(TimeUnit.MINUTES.toMillis(10))`; `spring.mvc.async.request-timeout` is set to 600 000 ms in `application.yml` to match, preventing the servlet container from closing the async request before the emitter signals completion. **Subscriber caps:** `subscribe()` now checks a per-session cap of 12 (2× MAXIMUM_PLAYERS, to allow reconnect churn) and a global cap of 500 before adding an emitter; a caller that exceeds either ceiling receives a `TooManySubscribersException`, mapped to HTTP 429 by `GlobalExceptionHandler`. The global count is tracked with an `AtomicInteger` decremented in `forgetOne()`. **Heartbeat stall fix:** `beat()` submits each emitter's send as a task to a bounded four-thread `sse-send-N` pool instead of calling `send()` inline on the scheduler thread; the heartbeat thread enqueues all tasks and returns immediately, so a slow or stuck reader can block only one of four workers rather than the entire sweep. **Shutdown:** `destroy()` now calls `heartbeats.awaitTermination(5, TimeUnit.SECONDS)` after `shutdownNow()`, and then shuts down the send pool with the same two-step.

- **`POST /api/v1/sessions` was unbounded: an unauthenticated caller could flood the join-code keyspace and exhaust the database (EOP-19, ADR-033).** Creating a session requires no credential and inserts a permanent row. Without a limit, a single caller could fill the `game_session` table at network speed — at 500 req/s that is 43 million rows per day — consuming every six-character join code and causing legitimate facilitators to receive opaque 503s once the five-attempt collision retry exhausts. Three controls now bound the attack surface. **Session creation limiter:** `POST /api/v1/sessions` is rate-limited to `eop.web.session-creation-limit` creations per address per 60-second sliding window (default 5). The slot is reserved atomically *before* any database work via `SessionCreationLimiter.recordCreation`, so a refused request never commits a row; if the downstream use case fails after the slot is reserved, `refundCreation` returns it so that a transient error does not permanently consume a creation allowance. The limiter is fail-closed on saturation: when the tracked-key table reaches 10 000 entries and a new address arrives, the attempt is refused before any database work rather than silently admitted — a flood of distinct keys is itself an attack pattern. **Request body cap:** Caddy enforces `request_body { max_size 16KB }` on all `/api/*` routes, rejecting oversized bodies at the proxy before they reach the application. This is the only body-size layer; there is no application-side cap, and direct access to port 8080 (bypassing Caddy) is unprotected — a known and accepted limitation recorded in ADR-033. **Neutral exception type:** the new `RateLimitedException` (use-case layer, no Spring imports) carries `retryAfter()` and produces a problem detail with title `"Too many requests"`, accurately describing a creation throttle rather than the join-attempt vocabulary the previous implementation reused. `GlobalExceptionHandler` maps it to HTTP 429 with a `Retry-After` header. The join-attempt limiter is unchanged and continues to throw `TooManyJoinAttemptsException`. **Configuration:** the limit is bound via `TrustedProxyProperties` (`@ConfigurationProperties(prefix = "eop.web")`), which already owns the `eop.web` namespace; `sessionCreationLimit` is a new `@Min(1)` field with default 5. The test suite overrides it to `Integer.MAX_VALUE` in `application.properties` to prevent exhausting the limiter across the shared Spring context; a dedicated `@SpringBootTest(properties = "eop.web.session-creation-limit=1")` scenario exercises the 429 path through the full HTTP stack. **Accepted limitations:** the counters are in-process memory and are forgotten on restart (a restart is a deployment, not something an attacker can trigger); horizontal scaling multiplies the effective limit by the instance count (there is one instance, ADR-012); NAT'd users share one bucket; and address rotation sidesteps the per-address window. All four are recorded in ADR-033

- **`InMemoryJoinAttemptLimiter` was fail-open on saturation and non-atomic on check-and-record (EOP-18, ADR-019).** Two independent defects. First: when either map reached `MAX_TRACKED_KEYS = 10 000` entries and a new key arrived, the old `remember()` silently returned without recording or refusing — a new address was admitted with no counter, so the ten-failures-per-address limit never fired for it. Second: `checkAllowed()` and `recordFailure()` were separate non-atomic operations; two concurrent threads both at `limit - 1` could both pass `checkAllowed`, both proceed to the database, and both record — so the effective limit was `limit + concurrency - 1` rather than `limit`. Both defects are now closed. **Fail-closed on saturation:** `checkAllowed` now calls `checkSaturation` for both maps before any database work; if a map is full and the key is new, it first attempts to evict windows whose entries have all aged out of the sliding window, and if the map is still full after eviction it throws `TooManyJoinAttemptsException` immediately. `recordFailure` silently drops the record for a saturated map — the key stays untracked while the table remains saturated, so this caller's subsequent attempts are refused by `checkAllowed`'s saturation check. **Atomic check-and-record:** `recordInWindow` acquires `synchronized(window)` on the deque before pruning, checking the allowance, and appending the new timestamp; this is the only site that mutates a window deque. `checkAllowed` is a best-effort pre-check that takes no lock on the window deques; it may evict aged-out map entries via `evictEmptyWindows` (a map mutation, not a deque mutation), and avoids database work for clearly over-limit callers. **Both windows always evaluated:** `recordFailure` records in both the address window and the code window regardless of which one is saturated — silencing the per-code counter under address-table saturation would disable the control that defends against a distributed enumeration attack. **Port contract updated:** `JoinAttemptLimiter.recordFailure` now declares `@throws TooManyJoinAttemptsException` to match the implementation. Three documents updated to reflect the new behaviour: `docs/architecture/C4-Diagrams.md`, `docs/architecture/runtime-view.md` and `docs/adr/ADR-019`

- **Two reachable exceptions had no mapping, so ordinary seat contention answered 500 with a stack trace.** `JoinSessionUseCase` retries a contested seat up to `MAXIMUM_SEAT_ATTEMPTS` times and then rethrows the last `SeatAlreadyTakenException`; `CreateSessionUseCase` rethrows `JoinCodeUnavailableException` after five consecutive join-code collisions. Neither had an `@ExceptionHandler`, so both fell through to `handleUnexpected` — 500, plus a full trace at ERROR, on a path that is not a malfunction at all. `GlobalExceptionHandler` now maps `SeatAlreadyTakenException` to **409** and `JoinCodeUnavailableException` to **503** with `Retry-After: 5` (EOP-17, ADR-005, ADR-019). Four decisions are worth naming. **Neither response echoes its exception's message.** `SeatAlreadyTakenException` builds its message from the session UUID and the seat order, and a joining caller supplies only a join code — so returning `getMessage()` would hand back an internal identifier the caller never held; `JoinCodeUnavailableException`'s message describes our own generator colliding with our own data, which is of no use to someone who never sees a code being generated. Both handlers therefore set a fixed detail, following the precedent already set for an unknown join code. **The two paths log at different levels, and that asymmetry is the point rather than an inconsistency.** Seat contention is provokable at will by anyone holding a valid join code — roughly twenty concurrent joins against one lobby will do it — so it logs at DEBUG *without the throwable*: mapping it to 409 while still writing a WARN and a stack trace per occurrence would have relocated the log-flooding amplifier instead of removing it, and the flooding is half of what this ticket exists to fix. Join-code exhaustion cannot be provoked, needing a run of independent collisions across the whole attempt budget, so each occurrence is genuine evidence that the live-lobby count is approaching what a thirty-bit code space bears, and it logs at WARN with the throwable — the handler being the only place that evidence ever appears. Neither logs at ERROR, which is what the acceptance criteria asked for, and the tests assert the level and the absence of a `throwableProxy` rather than only the status, because a status assertion alone passes just as well against a handler that logs at ERROR. **The 503 is a capacity statement, not an error**, which is why it carries `Retry-After` like the 429 does and why five seconds is documented as a defensible guess rather than a derived figure: there is no queue draining at a known rate to compute it from, and it only has to be short enough that a facilitator retries and long enough that a client honouring it does not immediately re-run the same exhausted loop. **The unit tests could not have caught what escaped.** What reached `main` was not a wrong handler but an absent one, and an absent handler is invisible to a test that names the handler it expects — so `SessionContentionIntegrationTest` drives both paths through the full web adapter and proves Spring dispatches to the new methods rather than to the catch-all, using a `@Primary` decorator over `SessionRepositoryAdapter` with two independent switches because neither path can be provoked honestly and filling the lobby to six raises the already-mapped `SessionFullException` instead. Its third test creates and joins with both switches closed, guarding the acceptance criterion that untouched paths stay untouched. The shared `Conflict` response in `docs/api/openapi.yml` now enumerates fourteen titles rather than thirteen, the count having been wrong in the direction the prose itself warns about, and a new `ServiceUnavailable` response documents the 503. This unblocks EOP-25, which may not flip `eop.features.session-lifecycle` on until every gate ticket is closed; the flag remains off

- **`docs/devops/local-development.md` claimed the front end was not yet scaffolded.** The section heading read "NOT YET SCAFFOLDED", a status blockquote asserted "There is no `ui/` directory in the repository yet", and the Common Commands section said front-end commands were "not available yet". `ui/` has been scaffolded and tracked since ADR-009 was implemented — it carries `dev`, `build`, `typecheck`, `lint`, `test`, `test:watch`, `verify`, `prebuild` and `predev` scripts, a Vite proxy to `:8080`, a Caddy image, and a `ui` CI job that runs all quality gates. The section is rewritten to describe what exists rather than what was planned (EOP-000)

- **Replaying a trick resolution answered 500 instead of 409, and the class comment said it could not.** `TrickPlayRepositoryAdapter.recordResolution` mapped a zero-row outcome from the winner update to `IllegalStateException`, ten lines below a paragraph promising that a zero row count "is never treated as success and never rethrown as a server fault". The path is reached by an ordinary replay rather than by anything exotic: `advanceLeaderSeat` sets `current_leader_seat` where it already equals the seat it compared against, so whenever the seat that led a trick also *wins* it the guard is idempotent, a replayed request gets past the statement meant to stop it, and the winner update — guarded by `winner_play_id IS NULL` — is the first to notice. It now raises the new `TrickAlreadyResolvedException`, which the handler maps to 409 naming the trick the caller supplied and deliberately not the winning seat, that being the answer to the question the caller was asking and the read model's to give. The existing second-resolution test never covered this because its fixture happens to produce a winner who is not the leader; the new test forces the case and would fail both against the old mapping (Spring translates `IllegalStateException` out of a `@Repository` into `InvalidDataAccessApiUsageException`) and against no guard at all. Found by the security review gate, not by the build, which was green throughout
- **Four exception accessors had no test, and a mutation returning null survived the suite.** The `sessionId()` accessor on `HandAlreadyDealtException`, `HandNotDealtException`, `PlayerNotInSessionException` and `SessionNotFoundException` was measured at 75% instruction coverage, the gap being exactly the accessor body. It is not decoration: `GlobalExceptionHandler` builds problem details from accessors rather than `getMessage()` so that it can choose which identifiers to disclose, so an accessor returning null would either print "null" into a response body or throw inside the handler and turn a mapped 404 into a 500. `SessionBearingExceptionTest` now covers all four, pins each against two distinct instances so a hard-coded constant cannot pass, and asserts the stranger/missing-session message parity at the constructors where a divergence would actually be introduced. Measuring the whole tree afterwards found five more classes with the identical gap that no gate had named — `TooFewPlayersException`, `SessionFullException`, `NotFacilitatorException`, `SessionNotJoinableException` and `PlayerNotRecognisedException`, all at 65–75% — and they are covered here too, including the second field each carries beyond the session identifier, because it is the capacity or the seated count or the status that a refusal actually needs to name. Classes below 80% instruction coverage fell from seven to two
- **Three documents still asserted a containment the previous commit had already falsified.** Mapping the five trick-play tables made "no entity, adapter or route" false, and the correction landed in `C4-Diagrams.md`, `runtime-view.md` and one place in ADR-023 — but three further claims in ADR-023 survived it, because the correction there scoped itself to "the two paragraphs above" and a reader who stops at a false sentence never follows a pointer. All three are now corrected **at the claim**: that no adapter, repository or entity maps `trick` (the winner-play gap is now held shut by `winnerAmong` revalidating on every read, which is weaker than the structural impossibility claimed, and only "no route" survives of the original containment); that `current_leader_seat` is "mapped by no entity, written by no code"; and that Slice B's five tables have "no entity, adapter or route". The same amendment discharges a self-test ADR-023 had set and nobody had marked passed — changeset `005` landed all three demanded bounds together, derived from `GameSession.MAXIMUM_PLAYERS` rather than hard-coded — and records the one bound still missing, `trick.leader_seat`, which has no CHECK and is refused only by the domain on read
- **`eop.features.session-lifecycle: off` silently enabled the lobby it was meant to withhold.** `SessionController`'s `@ConditionalOnProperty` named the property without naming the value it wanted, and in that form Spring matches any value present that is not literally `false` — so `off`, `no`, `0` and `disabled` all switched the five session routes *on*. `off` is the worst of the four: it is the word an operator reaches for when they want a kill switch, and in YAML 1.1 it is a boolean false, so a hand-edited `application.yml` reading `session-lifecycle: off` looks correct to every reader and to the YAML specification while enabling the feature. The condition now carries `havingValue = "true"`, as ADR-013 requires of every flag in the repository, so a flag's off position is every value except one rather than one value except everything. **The controller was the symptom and not the whole defect.** `createSessionUseCase`, `joinSessionUseCase`, `getSessionStateUseCase` and `startSessionUseCase` were registered unconditionally, so the beans that open and mutate a session existed whatever the flag said and only the route was ever withheld — which is why the loose condition had nothing to fail against and no startup error ever signalled the mistake, unlike `TrickController`, whose sibling defect (fixed in `56c31b1`) fell over at once because its use cases already required `"true"`. All four are now gated on the same flag, which is what makes the off position a property of the context rather than of one bean. `resolvePlayerUseCase` is deliberately left **ungated** and that exception is load-bearing rather than an oversight: it writes nothing, the five trick-play use cases depend on it too, and gating it on the lobby flag would make trick play unsatisfiable in the configuration the suite actually runs — lobby off, trick play on — following the precedent of the ungated `DeckShuffler`. **The fix is proved by a second spelling, because the first could not have caught it.** `SessionControllerDisabledIntegrationTest` uses the literal `false`, which was never the broken value; it passed before this change and after it and is left byte-identical, so the new `SessionLifecycleOffValueIntegrationTest` pins `off` instead, asserting the controller and the four use-case beans absent, `resolvePlayerUseCase` and `PlayCardUseCase` present, and all five routes 404. Run against the pre-fix code it fails six of its twelve tests — and the shape of that failure is the argument for asserting beans as well as statuses: the five bean assertions fail, and of the five routes exactly one does, `POST /api/v1/sessions` answering **201 Created** and persisting a session with the flag set to `off`. The other four returned 404 either way, because a random session identifier and an unissued join code are absent whether or not the controller is. A status-only test would have caught this on one route out of five and only because that route creates something. Exposure was latent rather than live — `application.yml` ships the literal `false` — but the flag failed open, against the plain requirement in `.opencode/rules/security.md` that a control fails securely. **The set of values that enabled it was wider than first reported.** The security gate read the resolved `spring-boot-autoconfigure` bytecode rather than the documentation and found the loose condition reduces to `!"false".equalsIgnoreCase(value)`, so the **empty string** enabled the feature too — `EOP_FEATURES_SESSION_LIFECYCLE=` exported empty being the likeliest way an operator unsets a variable while leaving it present. An absent property was never the hole, `matchIfMissing` already defaulting to `false`; the hole was confined to the present case, and there is now no value an operator can reach for other than the six letters `false`. **Five documents asserted the unfixed state and all five were corrected in this commit,** because a change that fixes the code and leaves the register describing the vulnerability is the defect this changelog has penalised before: ADR-013 (whose note said the controller "still carries the loose form" with "unconditional" beans, and whose mandate now also requires the flag on every bean that opens or mutates the state behind it, not the controller alone), ADR-028 (one of whose three predecessors is discharged), `docs/adr/README.md`, `docs/architecture/C4-Diagrams.md` (which quoted the annotation without `havingValue` and carried a live paragraph headed "One wart worth recording"), and `application.yml`'s own two flag comments. Note the consequence for whoever flips the flag next: only the literal `true` now turns it on, so `on`, `yes` and `1` are silent no-ops. Found by the security review gate during EOP-14 Slice D, graded HIGH by the architecture review, and made a precondition of EOP-25 and of flipping trick-play on (EOP-48, ADR-013)

- **The replay that passes
 a compare-and-set is now a recorded decision, not a Javadoc comment.** Fixing the 500 above revealed something the design did not state anywhere: `advanceLeaderSeat` compare-and-sets the session row like the other four conditional writes, but it is **not** a replay guard, because when the seat that led a trick also wins it the statement writes the value it just compared against and is idempotent. Trick resolution is therefore serialised by `winner_play_id IS NULL` on the *trick* row — the one place in the design where the contended row is not the session row. An architecture gate observed that this slice had remediated one decision-in-a-Javadoc while introducing another, and that the new one qualified the very guarantee the remediation asserted; ADR-020 now carries both, including that the two second-resolution shapes (`OutOfTurnException` when the lead moved, `TrickAlreadyResolvedException` when it did not) do not subsume each other. The duplicate is deleted, the test re-anchored, membership now read from the backticked tokens of the two blocks that enumerate the groups, and both groups located positionally rather than one being inferred by subtracting the other — which is how `CardNotInHandException` was mis-filed in the first place. - **`X-Forwarded-For` was believed from any caller, so the join-code throttle could be bypassed by rotating one header.** The application read the last entry of the header and used it as the client address — the key the join-attempt limiter counts failures against. The reasoning was that Caddy is the only published entry point (ADR-017) and Caddy appends to the header, so the last entry is the one the proxy wrote: sound, but valid only if the peer really is the proxy, and nothing checked that. Reached directly — by `./mvnw spring-boot:run` on port 8080, from a sibling container on the Compose network, or through any later change that publishes the application port — a caller supplied its own rate-limiter key, and a fresh value per request meant a fresh empty bucket per request, so the ten-failures-per-address limit never fired. The per-code counter could not compensate, because a code-guessing attacker uses a different code every time. ADR-019 designates that limiter a *primary* security control rather than defence in depth — a six-character join code is thirty bits, unguessable only while guessing is slow — so this was not a thinned-out layer but the removal of the control the entropy budget was calculated against (EOP-26, ADR-021)
- **Trust in a forwarding header is now an explicit, default-denied allow-list.** `eop.web.trusted-proxies` holds literal addresses or canonical CIDR blocks; the header is ignored entirely unless the peer address is on that list, and the default is empty, so an application deployed without a thought about forwarding headers trusts nobody and keys on the peer. A malformed or non-canonical entry fails startup rather than being skipped — silently masking `10.0.0.5/8` to `10.0.0.0/8` would trust sixteen million hosts where the author plainly meant one. Every resolved address is canonicalised before it becomes a map key, because two spellings of one address are two buckets, which is the same defect arriving by another route. `server.forward-headers-strategy` is pinned to `none` in both profiles so neither Tomcat's `RemoteIpValve` nor Spring's `ForwardedHeaderFilter` can launder the header into `getRemoteAddr()` behind the check: their default trust lists cover `172.16.0.0/12`, which contains this project's own Compose subnet. The deployed value sits beside the proxy's pinned container address in `compose.app.yml`, so the two halves of one fact cannot drift apart (EOP-26, ADR-021)
- **A green build had been evidence that the bug was still present.** The integration suite's `freshAddress()` helper gave each test its own throttle bucket by setting `X-Forwarded-For` — a test choosing its own rate-limiter key from outside the process, which is precisely the attack. The suite had been getting its isolation *from the vulnerability*, so closing the hole broke sixteen previously-passing tests. Trusting `127.0.0.1` suite-wide would have let all sixteen pass unchanged and was rejected: it would have re-opened the hole everywhere in the suite except in the tests that assert it is closed. The helper is now `unusedAddressHint()`, documented as having no effect, and the throttling tests get a fresh limiter from `@DirtiesContext` instead of from a forged header (EOP-26, ADR-021)
