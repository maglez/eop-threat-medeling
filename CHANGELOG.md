## [1.0.0-SNAPSHOT] — Unreleased

### Added

Working code and tooling that exists in the repository today.

- Walking Skeleton: Spring Boot 4.1.0 + Java 21 + `GET /health` (ADR-002)
- Continuous integration: GitHub Actions running `./mvnw verify` on push and PR, uploading the built artifact, then building the container image, smoke testing it against a real PostgreSQL and publishing it to GHCR on `main`
- Front end: React + TypeScript + Vite under `ui/` with GOV.UK Design System CSS (ADR-009). One page — the application shell plus the card catalogue fetched live from the API. Both calls to action are visibly disabled, because a button that looks live and does nothing is worse than one that admits it
- Single-origin serving: Caddy serves the built front end and reverse-proxies `/api/*` and `/health` to the application on the same origin (ADR-017). The application container publishes no host port at all, so there is no cross-origin request anywhere and therefore no CORS configuration to maintain
- Front-end quality gates: a dedicated `ui` CI job runs type checking, linting, unit tests and the production build as four separate steps. It is deliberately separate from the Java `build` job — the single required status check protecting `main` stays Java-only and fast, and a front-end failure reports as a front-end failure
- Container images: multi-stage `Dockerfile` producing a non-root JRE image and `ui/Dockerfile` producing a Caddy image carrying the built front end, `compose.app.yml` running both alongside containerised PostgreSQL, published to `ghcr.io` by CI with no repository secrets (ADR-012, ADR-017)
- Deployment infrastructure: Terraform under `infra/` describing a single `t3.small` EC2 instance in a dedicated VPC with an Elastic IP and a separate encrypted EBS data volume (ADR-012). Validated with `terraform validate`; no `apply` has run yet because no AWS account has been provisioned, and cloud deployment is deferred in favour of running locally (see the ADR-012 amendment)
- Local container runtime: Colima provides a Docker-compatible daemon from Homebrew formulae with no administrator rights (ADR-016). The whole stack — application and PostgreSQL — now runs on a developer machine with the same `docker compose -f compose.app.yml up -d` that CI and the EC2 bootstrap script use
- Build quality gates: Checkstyle (`checkstyle.xml`), SpotBugs, JaCoCo 80% instruction coverage, Enforcer (ADR-006)
- Database migrations: Liquibase with a master XML changelog, H2 in the default profile, PostgreSQL in `prod` (ADR-008). The first migration creates the `card` table; the second replaces the placeholder deck with the real one
- Card catalogue: `GET /api/v1/cards` and `GET /api/v1/cards/{cardId}` serve the deck as read-only reference data (EOP-6)
- The real Elevation of Privilege deck: all 78 cards, thirteen ranks in each of the six STRIDE suits, transcribed from Microsoft's published deck and seeded by an additive data-only migration (EOP-13). © 2009 Microsoft Corporation, licensed CC-BY-3.0 US — attribution is the only obligation the licence imposes and it is discharged in the running application, not merely in the repository. The printed deck held 74 because two suits started above the two; the published machine-readable file completes them to thirteen apiece, which also removes two suit-specific special cases from the trick rules still to be written
- Trick-taking rules as pure domain types: `Hand`, `Hands`, `Trick` and `TrickPlay` under `org.maglez.eop.entity`, with zero framework imports, carrying the whole rule set the game turns on — dealing, following suit, turn order, and who takes the trick (EOP-14, ADR-023). Four decisions are worth naming. **The opening lead is derived, never written down:** the seat holding the lowest-ranked Tampering card *actually dealt* leads, because the printed 74-card deck starts on the three and the seeded 78-card deck on the two, and both are right for their own deck — a literal `2` or `3` anywhere in this code would be a defect against one of them, so `Hands.openingLeaderSeat()` computes it and `NoTamperingCardDealtException` covers the one case the rule cannot answer rather than falling back to an arbitrary leader. **Every card is dealt**, with the remainder going to the lowest seats, so at four and five players hands are unequal and the final trick is short; setting the remainder aside instead would have been tidier but can orphan the card the opening-lead rule needs, turning a derived rule into a hidden fallback reached only at certain player counts. That in turn makes a trick *one card from each seat that still holds cards* rather than a fixed count, so turn order is "the next seat clockwise still holding a card" and not the leader's seat plus the number of cards played — the simpler formula is correct for every trick except the last one at four and five players, which is why ADR-019 now carries a dated amendment where an implementer would otherwise copy it. **A card played with no threat linked is a legal, ordinary play:** it still competes for the trick and simply scores nothing, so `TrickPlay.threatLinked` is a fact about a play and not an error, and a linked threat naming no component is accepted too — a facilitation tool that refuses a play in a live session because a text box is empty gets in the way of the conversation it exists to support. **A card named in a request is resolved out of the hand before any rule is applied to it,** and there is one guarded way in: `Trick.acceptPlay` checks the turn, resolves the card, checks follow-suit against the *resolved* suit and appends the play, with `Trick.play` reduced to package-private so nothing outside the domain can reach the unguarded mutator. A card is named by identifier, so its suit and rank travel as the caller's *claim*; checking possession by identifier and then reading the suit off the submitted object let a holder of the two of Tampering submit that identifier labelled ace of Elevation of Privilege, pass possession, escape follow-suit because the claimed suit was trump, and take the trick with a card that was never dealt. Three public checks a caller was merely *documented* to call in the right order were two optional guards in front of an open mutator, not defence in depth. **The acting seat is a parameter in its own right and is never read from the payload:** `acceptPlay(int actingSeat, TrickPlay candidate, Hands hands)` takes the seat the caller has authenticated, refuses the play with `NotYourSeatException` if it describes a different seat, and then *derives* both the hand and the set of seats still holding cards from `hands` rather than accepting either. An earlier revision took the seat from the submitted play and cross-checked only the hand against the player, which is a two-way check on a three-way fact — seat, hand and player — and `Hand` deliberately carries no seat number, so the binding could not be made from those arguments at all. Because the session state already publishes every player's identifier *and* seat to every other player, a player really sitting at seat 2 could submit its own identifier with someone else's seat number and its own hand: the play was accepted out of turn, the victim's seat was marked as having played so they were locked out of the trick for good, and the attacker could then play a second card from the same hand at its real seat and take the trick. The player identifier remains the one caller-supplied claim, and it is checked against the seat's occupant rather than believed. **The seat is settled before anything else is looked at** — whether it is a seat at this table at all, whether the play claims that seat, and whether the player the play names is the one occupying it — because all three are answered entirely from facts the requester already sent, so a refusal discloses nothing it did not already know. A play naming a seat's non-occupant is refused with `PlayerMismatchException`, its own type rather than a bare `IllegalArgumentException`, so the boundary can tell impersonation from a malformed argument without matching on message text and can carry both player identifiers as fields instead of interpolating them into a message a caller reads. Turn order comes next, before the card is looked at, so a player who is not to play learns nothing about their own cards from the refusal, and `Trick.nextLeaderSeat(seatsHoldingCards)` passes the lead on when the winner has run out of cards — a winner's seat handed back unconditionally would open a trick nobody could play into, which is reachable at four and five players and would have stopped the game with no exception to log. Free text a player types is bounded and refused if it carries control characters or bidirectional overrides, because a NUL byte cannot be stored in a PostgreSQL `text` column, CR and LF in text that reaches a log let a player forge log lines, and a bidi override lets a component name display differently from the one stored. On rendering: `Hand`, `Hands` and `TrickPlay` print only counts, because knowing an opponent's cards is knowing what they can and cannot follow with, and the default rendering would leak a hand — or a player's notes — into any log line that interpolated it. `Card.toString` drops its threat prompt as bulk rather than as a secret; the deck is published, so what is confidential is the *association* between a player and an unplayed card, and that guarantee lives in the redacted containers and in `Hand.cards()` being documented as confidential rather than in `Card` itself. A `Trick` also refuses, at construction, a play list in which one player holds two seats or two plays share an identifier, and refuses plays that do not run clockwise from the leading seat — the first of those is the stored form of the seat-impersonation defect above, and all three are checks a trick can make from the plays alone. What it cannot check is follow-suit, because that is a question about a hand and a trick holds no hands, so `Trick.reconstitute` is documented as **not** a validating gate for the rules of play and Slice B's persistence adapter must be trusted to store only what `acceptPlay` produced. `Hands.deal` refuses two seat assignments sharing a seat order, which previously collapsed silently on insertion and left one seat holding two round-robin shares of the deck. `docs/requirements/PRD-eop-card-game.md` §3.3 now carries dated deviation notes against the two sentences the implemented rules depart from — "one time around the table" and "the winner of a trick leads the next trick" — each linking ADR-023, because both are the shipped instruction card's wording and both are right for a game in which every hand empties together. All six of the story's domain refusals are now mapped to problem details and unit-tested, as the error-handling rules require of every known exception: a play claiming a seat its requester does not occupy and a play naming a player who does not hold that seat are both **403**, being impersonation rather than malformed input; a play out of turn is **409**; a play that breaks follow-suit, or names a card the hand does not hold, is **422**, because every field parsed and the refusal came from a rule of the game. Two of those mappings deliberately do not echo the exception's message: the card refusal reports only the card identifier and not the identifier of the hand, and the player-mismatch refusal returns a fixed sentence, its message having been reduced to name a seat and nothing else so that logging it cannot leak either player. A deck with no Tampering card is the one **500** here, because the deck is seeded reference data and every valid deck contains the suit. Nothing is wired up yet — no schema, no endpoint, no dealing on session start — and scoring is EOP-15
- Storage for the trick-taking domain: migration `004-trick-play-schema.xml` creates `hand`, `hand_card`, `trick`, `trick_play` and `trick_play_component`, and adds `game_session.current_leader_seat` (EOP-14, ADR-023). It also adds `uq_player_id_seat` to `player`, a table it does not create. The schema lands before the JPA entities and adapters deliberately, because `ddl-auto: validate` fails startup on an entity with no matching table. Six decisions are worth naming. **`trick_play.components` becomes a child table with an explicit `ordinal`, and the 20-element cap is enforced three times over** — once in the domain constructor, once in storage as `PRIMARY KEY (trick_play_id, ordinal)` plus `CHECK (ordinal >= 0 AND ordinal <= 19)`, and once at the boundary in the slice that adds the request DTO. That is defence in depth rather than duplication: the domain stops bad input, the constraints stop a bad write from a future adapter bug or a hand-run statement. `(trick_play_id, component_name)` is deliberately *not* unique, because the domain accepts repeated component names and a stricter constraint would turn a legal play into a 500. **`hand_card` gets no ordinal**, which looks inconsistent next to the components table until you notice that `Hand` sorts its cards in its own constructor so that two hands holding the same cards compare equal whichever order they arrived in — dealing order carries no meaning, whereas the order a facilitator typed their component names in does, so one is canonicalised and the other preserved as typed. **`trick` gets no `led_suit` column**, because `Trick.ledSuit()` derives it from the first play and a stored copy would be a second authority no write path populates. **The three `trick_play` unique constraints carry the invariants through a reload**, so they survive rather than living only in whichever entity happened to be in memory — but only one of them is the stored form of a Slice A security defect. `(trick_id, card_id)` closes card forgery within a trick. `(trick_id, player_id)` stops one player occupying two seats in a trick, which is a *different* exploit from the seat impersonation Slice A had to fix twice, and an earlier draft of this entry claimed otherwise. **Seat impersonation is closed instead by binding a stored seat to the seat its player actually holds:** `uq_player_id_seat` on `player (id, seat_order)` gives a composite foreign key something to reference, and `fk_hand_player_seat` and `fk_trick_play_player_seat` then make a hand or a play at a seat its player does not hold structurally unrepresentable, rather than merely unlikely. That reverses a deferral taken earlier the same day: the seat and cross-session protections were argued as one problem and a sound objection to the expensive half — denormalising `game_session_id`, a copy that can disagree with its parent — was allowed to carry the cheap half with it, when in fact `seat_order` was already on both tables and the binding needed one unique constraint that adds no invariant of its own. The single-column keys to `player(id)` are subsumed by the composite ones rather than omitted, and that subsumption holds only while both key columns stay `NOT NULL`. **What is deliberately still not enforced is session scoping**, and the honest consequence is that the composite key proves a player holds that seat *somewhere*, not that they are at this trick's table — seats are numbered from zero in every session, so a player at seat 2 in another session still satisfies it and can still take this session's seat-2 occupant out of play. Narrowed to cross-session attackers, then, not closed; it is owned by Slice C's play use case, which resolves the acting player from the identity token, and ADR-023 records both the reversal and what remains. **Foreign keys were missing on `trick_play.card_id` and `trick.winner_play_id`** and are now present; an unconstrained `card_id` in particular left card forgery re-openable one layer below the code that had just been hardened against it. `fk_trick_winner_play` is `ON DELETE SET NULL` rather than the `NO ACTION` first written, because measurement showed NO ACTION made a resolved trick undeletable outright — at the cost that deleting a winning play directly now silently unresolves its trick, which nothing but a comment currently prevents a later slice from doing. The concurrency test ADR-023 places in this slice rather than a later one — before the constraint exists there is nothing to assert against — drives one player racing itself through separate JDBC connections, which is the ordinary double-tap a real client produces; a second, sequential test uses two players from different sessions who both legitimately hold the same seat number, because that is the only construction left in which `uq_trick_play_trick_seat` is the sole constraint that can fire, and it doubles as the recorded proof of the cross-session gap above
- Range bounds on every seat and sequence column: migration `005-seat-and-sequence-bounds.xml` adds `chk_player_seat_order`, `chk_trick_sequence` and `chk_game_session_current_leader_seat` (EOP-14, ADR-023). This closes a gap found by measurement rather than by reading: against the merged Slice B schema, `player.seat_order = -7`, `trick.sequence = -5` and `game_session.current_leader_seat = 9999` were all *accepted* by the engine, while the domain refuses all three. Three points are worth naming. **One CHECK on `player.seat_order` bounds three tables**, because `fk_hand_player_seat` and `fk_trick_play_player_seat` bind `hand` and `trick_play` to `player (id, seat_order)` — so the seat range on the child tables is inherited, and the composite keys that carry it prove consistency with the parent but never validity, which is exactly why the parent needed a bound of its own. **`trick.sequence` gets a lower bound only**, because no upper bound is derivable — a three-player deal runs to 26 tricks and no domain constant caps it — so `>= 1` is the whole of what is known and inventing a ceiling would reject legal play. **The bounds are pinned to `GameSession.MAXIMUM_PLAYERS` by a test that reads the changeset XML**, since Liquibase cannot read a Java constant and the literal `5` is a hand-copied counterpart: raising the player cap without editing the migration would leave storage stricter than the domain and turn a legal join into a 500. Each constraint is tested in both directions, because a test that only proves rejection would pass just as well against a CHECK that rejected every value, legal ones included. Adding a constraint to `player` from a later changelog file rather than editing `003` is the only lawful option — merged changesets are immutable (ADR-008) — and follows the precedent `004` set when it added `uq_player_id_seat` to the same table. Writing all three as raw `<sql>` is likewise forced: `addCheckConstraint` is a Liquibase Pro change type and is absent from the open-source `liquibase-core` this project depends on. Landing `005` also exposed a latent defect in Slice B's own round-trip test, which rolled back a hard-coded nine changesets to undo `004` — correct only while `004` was the last changelog file, since Liquibase counts backwards from the last change *applied*. It now derives the count from `DATABASECHANGELOG`, so `006` cannot re-break it
- An error vocabulary for trick play: seven domain exception types and their problem-detail mappings — `PlayerNotInSessionException` (404), `HandAlreadyDealtException`, `HandNotDealtException`, `TrickAlreadyOpenException`, `AlreadyPlayedInTrickException` and `CardAlreadyPlayedException` (409), and `WinningPlayNotInTrickException` (422) — landing ahead of the use cases that will throw them (EOP-14, ADR-023). Five decisions are worth naming. **A caller who is not in the session is answered exactly as a session that does not exist**, byte for byte and not merely with the same status: a 403 would confirm to a stranger holding a guessed or leaked identifier that it guessed correctly, and two 404s with different titles would be as good an oracle as a 403, so the test asserts equality of the two whole `ProblemDetail` bodies. The parity is held in place by the exception itself, which builds the same message as `SessionNotFoundException` for the same identifier and carries the session id **and nothing else** — a field naming the player, the seat or the reason would eventually be logged into a response, and a field that does not exist cannot be. This follows the fixed-body reasoning already written for an unknown join code, with the one deliberate difference that a join code is blanked because roughly thirty bits are guessable while a caller-supplied session identifier can be echoed back safely. **The candour argument that licenses naming a missing session is now scoped in the code that makes it**: the Javadoc on `SessionNotFoundException` and its handler argued from a 122-bit identifier, which is sound about whether a session exists and says nothing about who may see it, so both now cross-reference the membership answer rather than leaving the next reader to generalise a correct argument past its premise. **A winner from another trick is 422 and not 409**, because a conflict entitles the caller to retry once the state moves on and no state this application can reach makes a play from one trick the winner of another; it is also logged at warning level with both identifiers and returns neither, since ADR-023 records that this check will never have a storage constraint behind it — the composite key that would provide one collides with the rule that lets a winning play be deleted — so the log line is the only evidence that will ever exist. **The two conflicts on a trick are kept apart**: one refuses a second play from a seat, the other one card appearing twice whichever seat played it, and a test pins the titles as unequal so that collapsing them into a single "conflict" cannot pass. **The two states of the deal are kept apart on the same reasoning, and naming the second of them is what took a seventh type**: `HandNotDealtException` is the mirror of `HandAlreadyDealtException`, the two being opposite states of one column — `game_session.current_leader_seat` — and a vocabulary naming only one of them forces the other to be reported as something it is not. Before it existed, that branch of `TrickPlayRepositoryAdapter.sessionMoved` answered `SessionNotJoinableException` carrying `IN_PROGRESS`: the right status with an explanation that contradicted itself, telling a caller a session was not joinable while handing back the status saying it was in progress. @architecture-guardian found it in this slice's architecture review, and the fix was a type that can name the state rather than a different status code — the branch is reached by asking to open the first trick before the deal, which is an ordinary caller mistake rather than a broken invariant, hence a 409 and not a 500. The two 409 titles are deliberately unequal, and a test pins that they do not collapse into each other, because both are conflicts on one column and the title is the only thing saying which way it went. The translation table in ADR-023 was also one row short and is amended here: `uq_trick_session_sequence` is reachable by two requests racing to open the same trick, and without a name for it that race answered 500. What C1 cannot yet test is the status over the wire, because it adds no route — the handlers are proved as pure functions here, exactly as the existing mappings are, and the wire-level assertions arrive with the endpoints
- Persistence mappings for the trick-play tables: JPA entities for `hand`, `hand_card`, `trick`, `trick_play` and `trick_play_component`, plus the `current_leader_seat` column on the session entity (EOP-14, ADR-023). The point of the commit is not the eight new classes but what mapping them switches on. `spring.jpa.hibernate.ddl-auto` is `validate`, and until now that setting was nearly free: three tables were mapped, the five created by Slice B were not, and Hibernate validated nothing about them — so a mapping could disagree with the migrations indefinitely and only a query that happened to touch the wrong column would ever say so. Mapping them means every column and type on all eight tables is now checked at every context start, on H2 in the suite and on PostgreSQL in production. Because that check is silent when it passes, it gets a test of its own rather than being left as something the other integration tests catch by accident: `MappedSchemaValidationIntegrationTest` asserts the effective `ddl-auto` value, so switching it to `none` fails loudly instead of quietly removing a guard, and then issues a real bounded `SELECT` of every mapped column of every entity, which is a stronger check than startup validation and one that names the entity when it breaks. The test was confirmed non-vacuous by measurement — renaming a single mapped column to `seat_ordering` turned all nine cases red — because a schema test that cannot fail is worse than none. Three mapping decisions carry reasoning. **No collection mappings anywhere**, following the session entity's existing refusal of `@OneToMany`: a played card is one delete and a play is one insert, and a cascade or orphan-removal mapping would turn each into a diff of two collections, which matters here more than it did for seats because the statement issued has to be exactly the statement it looks like — the row lock taken before it is the concurrency guard. **The two link tables use `@IdClass` rather than `@EmbeddedId`**, since both have a composite primary key that genuinely is their identity and no surrogate to invent; `@IdClass` keeps the key columns as ordinary fields, so a query reads `deleteByHandIdAndCardId` instead of routing every predicate through an embedded object. **`current_leader_seat` is mapped on the row and deliberately nowhere else** — the domain `GameSession` gains nothing, because the current leader is a fact about the trick in progress and `Trick` already derives whose turn it is from its own plays, so a copy on the aggregate would be a second authority on it. It is stored because it is the compare-and-set witness the conditional writes name, it is `Integer` rather than `int` because null is meaningful and is how "no cards dealt yet" is stored, and it advances once per trick rather than once per play. A play reads it and takes the row lock without changing it
- Storage for dealt hands and played tricks: the `HandRepository` and `TrickRepository` ports, five Spring Data interfaces, one `TrickPlayRepositoryAdapter` implementing both, and three further conditional updates on the session row — `claimDeal`, `touchWhileLeaderSeatIs` and `advanceLeaderSeat` (EOP-14, ADR-020, ADR-023, ADR-024). Five decisions carry the design and govern the first half of this entry; what follows them records what shipped, and the argument that used to fill the rest now lives in an ADR of its own. **There is no `save`**: each write is narrow and conditional on the state the caller observed, because a blanket save would have to diff an immutable aggregate against storage to learn which rows to write and could not be conditional on anything — which is precisely the compare-and-set turn order depends on. **Both ports are implemented by one class**, because playing a card deletes a `hand_card` row and inserts a play and its components and those must commit together; the two decompositions that keep one adapter per port either admit that torn state or put `@Transactional` in the use-case package. **Every write begins with a conditional update on the session row**, which is both the compare-and-set whose zero-rows answer means the world moved and the row lock taken in the order the ADR requires (session, then hands, then tricks). Zero rows is never success and never a server fault: one helper spends a single extra read on the already-failing path to answer that the session is missing, is not in progress, has already been dealt, has not been dealt at all, or that the caller's leader-seat snapshot is stale — the last being an out-of-turn play, since the leader seat is the value turn order is computed from, and a double resolution lands there too because the first resolution moved the seat. **Hands are read whole or not at all**, since `Hands.reconstitute` re-runs a cross-seat invariant no database constraint stands behind and a per-seat read would satisfy it vacuously, switching off its only enforcement; writes stay a one-seat delta. Plays are ordered by rotation from the trick's leader seat rather than by `played_at`, because the domain reads the led suit from the first play and a timestamp can tie. **The seat foreign keys are a backstop rather than the check**: the adapter reads the session's seats before inserting and refuses a wrong seat itself with 403, or an unknown player with the same 404 a missing session returns, and a key that fires anyway is logged at warning level with its constraint name and rethrown as a server fault, because it means a check above it was missed. Checking first is sound only because a seat never moves once seated — the column is mapped non-updatable — so unlike seat *allocation* there is no window to narrow. Each index maps to one exception, proved by driving the adapter through a live schema rather than a stub: `uq_hand_session_seat` becomes `HandAlreadyDealtException`, `uq_trick_session_sequence` `TrickAlreadyOpenException`, `uq_trick_play_trick_seat` and `uq_trick_play_trick_player` both `AlreadyPlayedInTrickException` — one player makes one play whichever index catches the second — and `uq_trick_play_trick_card` `CardAlreadyPlayedException`. Three details of that test are load-bearing: cards come from the seeded catalogue, because the domain's deck fixture mints synthetic identifiers `fk_hand_card_card` refuses; the class is not `@Transactional` and cleans nothing up, since the first violation marks a test-managed transaction rollback-only and would poison every later assertion, so each case mints its own identifiers and commits as production does; and two indexes must be reached deliberately, `uq_hand_session_seat` by nulling the leader seat *and* dealing fresh hand identifiers, because reusing them makes `saveAndFlush` merge and silently succeed, and `uq_trick_play_trick_card` by inserting a `hand_card` row by hand, since the adapter's own delete refuses the second play first. The negative controls are that a deal naming an unseated player, and one naming a seated player at somebody else's seat, each write *nothing*; and what the test cannot reach is recorded in it — the missing-card server fault, while the foreign keys make a referenced card undeletable, and both seat backstops, because the adapter refuses first, so a fired backstop's warning line is untested by construction. Two reads also turn out to throw `InvalidDataAccessApiUsageException` and not the JPA-specification `IllegalStateException` they appear to, because the adapter is a `@Repository` and Spring translates on the way out; both still fall to the catch-all 500, and the assertions pin that, since an `IllegalArgumentException` would render as a 400 and blame the caller for a fault of ours. Reading the leader seat revalidates the column against the domain's seat count, and a seat bound for a column is refused at the boundary rather than left to the CHECK; both guards are pinned as the pure functions they are, the read guard because it cannot be reached end to end at all — this slice's range constraint refuses the very row the guard exists to survive — and the write guard because only its negative limb is out of reach. The three range constraints carry preconditions that halt with the query to run instead of an engine error naming neither the row nor the reason. A security review rejected the slice for documentation claiming an authorisation this layer does not perform: it authorises nobody, none of its statements takes a player identifier, and the seat check is a check on the *row* rather than on the requester. [ADR-024](docs/adr/ADR-024-trick-play-persistence-boundary.md) now carries that decision, the argument behind it, and the obligation it puts on Slice C2 — authorise the requester first, in every use case, because no test here fails if you do not. This slice's documentation work landed with it: ADR-024 was created, and ADR-023, ADR-020, ADR-013, `docs/adr/README.md`, `docs/architecture/C4-Diagrams.md` and `docs/architecture/runtime-view.md` were corrected, because mapping the five tables falsified standing claims in three documents that the tables were unreachable — the containment is now the absence of a use case and a route rather than the absence of a mapping
- API contract: the hand-authored OpenAPI 3.1 specification at `docs/api/openapi.yml` (ADR-004), written before the controllers that implement it
- Error handling: a single `@RestControllerAdvice` rendering RFC 9457 problem details, with a unit test for every mapped exception (ADR-005)
- Feature flags: Spring configuration properties under `eop.features.*`, gated with `@ConditionalOnProperty` and no third-party library (ADR-013). One flag exists — `eop.features.session-lifecycle`, off by default, shipped with the session lifecycle (EOP-10) and pinned in both positions by tests
- Real-time transport and player identity: decided from a time-boxed spike that ran a real server-sent-events endpoint against the application (EOP-8). Server-sent events carry state to every connected player (ADR-014); a server-issued opaque token in per-tab session storage identifies a player (ADR-015). Both are decisions only — the spike code was deleted and no production code graduated from it

### Fixed

- **Replaying a trick resolution answered 500 instead of 409, and the class comment said it could not.** `TrickPlayRepositoryAdapter.recordResolution` mapped a zero-row outcome from the winner update to `IllegalStateException`, ten lines below a paragraph promising that a zero row count "is never treated as success and never rethrown as a server fault". The path is reached by an ordinary replay rather than by anything exotic: `advanceLeaderSeat` sets `current_leader_seat` where it already equals the seat it compared against, so whenever the seat that led a trick also *wins* it the guard is idempotent, a replayed request gets past the statement meant to stop it, and the winner update — guarded by `winner_play_id IS NULL` — is the first to notice. It now raises the new `TrickAlreadyResolvedException`, which the handler maps to 409 naming the trick the caller supplied and deliberately not the winning seat, that being the answer to the question the caller was asking and the read model's to give. The existing second-resolution test never covered this because its fixture happens to produce a winner who is not the leader; the new test forces the case and would fail both against the old mapping (Spring translates `IllegalStateException` out of a `@Repository` into `InvalidDataAccessApiUsageException`) and against no guard at all. Found by the security review gate, not by the build, which was green throughout
- **Four exception accessors had no test, and a mutation returning null survived the suite.** The `sessionId()` accessor on `HandAlreadyDealtException`, `HandNotDealtException`, `PlayerNotInSessionException` and `SessionNotFoundException` was measured at 75% instruction coverage, the gap being exactly the accessor body. It is not decoration: `GlobalExceptionHandler` builds problem details from accessors rather than `getMessage()` so that it can choose which identifiers to disclose, so an accessor returning null would either print "null" into a response body or throw inside the handler and turn a mapped 404 into a 500. `SessionBearingExceptionTest` now covers all four, pins each against two distinct instances so a hard-coded constant cannot pass, and asserts the stranger/missing-session message parity at the constructors where a divergence would actually be introduced. Measuring the whole tree afterwards found five more classes with the identical gap that no gate had named — `TooFewPlayersException`, `SessionFullException`, `NotFacilitatorException`, `SessionNotJoinableException` and `PlayerNotRecognisedException`, all at 65–75% — and they are covered here too, including the second field each carries beyond the session identifier, because it is the capacity or the seated count or the status that a refusal actually needs to name. Classes below 80% instruction coverage fell from seven to two
- **Three documents still asserted a containment the previous commit had already falsified.** Mapping the five trick-play tables made "no entity, adapter or route" false, and the correction landed in `C4-Diagrams.md`, `runtime-view.md` and one place in ADR-023 — but three further claims in ADR-023 survived it, because the correction there scoped itself to "the two paragraphs above" and a reader who stops at a false sentence never follows a pointer. All three are now corrected **at the claim**: that no adapter, repository or entity maps `trick` (the winner-play gap is now held shut by `winnerAmong` revalidating on every read, which is weaker than the structural impossibility claimed, and only "no route" survives of the original containment); that `current_leader_seat` is "mapped by no entity, written by no code"; and that Slice B's five tables have "no entity, adapter or route". The same amendment discharges a self-test ADR-023 had set and nobody had marked passed — changeset `005` landed all three demanded bounds together, derived from `GameSession.MAXIMUM_PLAYERS` rather than hard-coded — and records the one bound still missing, `trick.leader_seat`, which has no CHECK and is refused only by the domain on read

### Changed

- **The replay that passes a compare-and-set is now a recorded decision, not a Javadoc comment.** Fixing the 500 above revealed something the design did not state anywhere: `advanceLeaderSeat` compare-and-sets the session row like the other four conditional writes, but it is **not** a replay guard, because when the seat that led a trick also wins it the statement writes the value it just compared against and is idempotent. Trick resolution is therefore serialised by `winner_play_id IS NULL` on the *trick* row — the one place in the design where the contended row is not the session row. An architecture gate observed that this slice had remediated one decision-in-a-Javadoc while introducing another, and that the new one qualified the very guarantee the remediation asserted; ADR-020 now carries both, including that the two second-resolution shapes (`OutOfTurnException` when the lead moved, `TrickAlreadyResolvedException` when it did not) do not subsume each other. Three comments that had inherited the false premise are corrected: `GameSessionJpaRepository.advanceLeaderSeat` claimed to be the double-resolution defence, `GameSessionJpaEntity` still said "the two writes that matter", and `TrickRepository.recordResolution`'s `@throws` contract claimed `SessionNotJoinableException` covered "the case where another request resolved this trick first", which it never did, while declaring neither exception that actually refuses a second resolution. A later review round found the same contract *incomplete* as well as wrong — `OutOfTurnException` and `HandNotDealtException` were undeclared on `openTrick` and `appendPlay` too, though the suite proved both thrown — so all three write methods now declare every exception their shared zero-rows helper can raise. Three further inherited counts were wrong and are corrected — `GameSessionJpaRepository` said "two update methods" where there are five, `GameSessionJpaEntity` named one statement of five as the one holding the row lock, and `GlobalExceptionHandler` said `handleOutOfTurn` returns 422 when it has always returned 409 — as is one more containment overstatement, this time the adapter class comment claiming `DataIntegrityViolationException` "stops at this class" when an unrecognised constraint name is deliberately rethrown so a constraint added later fails loudly. ADR-023's note beside the translation table stated its own count four times and got it wrong three: two, then three, then six. The answer is **nine**, and nine counts domain refusals rather than every exception those paths can raise — `IllegalStateException` and `IllegalArgumentException` are server faults, not refusals a caller earns, which is why it is nine and not eleven. Every miss had the same shape: the shared `sessionMoved` helper has five answers, three kept being omitted while two were counted, and `OutOfTurnException` was omitted every time. The split is seven raised from a rows-affected count of zero (those five, plus a replayed resolution and a card no longer in the hand) and two from the `assertSeated` read; the six-count had also filed `CardNotInHandException` in the read group against its own stated criterion, when it comes from a conditional DELETE matching no row. Six of the nine have an origin in ADR-020, not three as an earlier version said while naming the wrong three, and two of the nine are dual — both a row of the table and a non-constraint origin.

  Three careful readers wrote those counts and three careful reviewers passed them, so the invariant is now machine-checked. `TrickPlayExceptionOriginTest` **derives** the set from the adapter by position — classifying each construction by whether it sits inside a `DataIntegrityViolationException` translation or not — and asserts the ADR names *exactly* that set. The first version of that test did not: it compared the prose against a hard-coded list while its Javadoc claimed to derive from the source, so a tenth origin in the adapter would have left the suite green, and both its assertions ran the same direction so padding the prose passed. Three review gates caught the overclaim independently. A further round found that the second direction was still not equality — padding was checked against a closed list of four types, so a fabricated name passed — and that the correcting edit had **duplicated** the ADR paragraph rather than replacing it, leaving the exact sentence the previous round had rejected alive four lines below its own correction, with the new test anchored on the stale wording so deleting it would have turned the build red. Three gates found that independently. The duplicate is deleted, the test re-anchored, membership now read from the backticked tokens of the two blocks that enumerate the groups, and both groups located positionally rather than one being inferred by subtracting the other — which is how `CardNotInHandException` was mis-filed in the first place. Verified by mutation: a tenth origin added to `sessionMoved` fails with `Expected size: 9 but was: 10`; a fabricated name in a group block fails, where it previously passed; and removing a real origin from the prose fails. One limitation is recorded rather than claimed away — a type a block mentions twice, once enumerating and once in narrative, survives deletion of the enumerating mention alone, which is why the validating mutation removes every mention. A ninth round then found the whole approach one shape wrong, and the diagnosis is the part worth keeping: the paragraph asserts a **mapping** from exception name to mechanism, and every check built for it verified **aggregates** of that mapping — a total, group sizes, a union, a disjointness. Aggregates over a mapping leave every permutation green by construction, however many you add, which is why each round closed a real hole and left the next one open in the same place. The gate proved it by moving an origin between the two blocks with both headings untouched — the exact mis-filing the block records as its own past mistake — and the build stayed green. Each block's names must now equal its own derived group, which let the aggregate assertions and the test method holding them be deleted. That is a narrowing as well as a strengthening: the deleted disjointness check caught a type belonging to both groups at once, and per-group equality does not. The test discloses that.

  Deliberately no tally here of attack shapes, assertion counts or which mutation trips what. Every such restatement in this entry has been wrong at least once, including the one that announced the counting problem fixed, and a tenth round found two more — a comment describing a disjointness check that had been deleted one commit earlier, and a claim that three attack shapes had previously passed when only one had. Those numbers live in exactly two places now: `ADR-023`'s paragraph, which `TrickPlayExceptionOriginTest` pins against the adapter source, and the assertion messages themselves, which cannot go stale because they are the thing that fires. The arithmetic in the universe sentence was also wrong: nine domain refusals plus those two server-fault types is eleven, not thirteen.

  The adapter class comment was wrong in the same area — it claimed "every violation this class has been taught to name is translated, and no other", when the rule is three-way: five of the seven names it knows are translated, the two seat foreign keys marked `Backstop only` are recognised and deliberately rethrown as a 500 because `assertSeated` passed on the same facts moments earlier, and an unknown name is rethrown unlogged. It also cited `backstopFired` as where the unknown-name rethrow is argued; it is argued on `mentions`. A fourth containment claim — the third copy of the one corrected in ADR-023, this time in changeset `004`'s comment on `winner_play_id` — is corrected at the claim, and the over-strong "the only thing zero can mean" on the winner update is narrowed to the two things it can actually mean

- **The deal-once gate is now a recorded decision rather than a Javadoc comment.** Taking `current_leader_seat IS NULL` as the definition of "not yet dealt" makes the *session row*, not a count of `hand` rows, the point at which dealing serialises. That was decided in code during this slice with its entire rationale in a repository comment and no presence in `docs/`, even though ADR-020 owns session concurrency control and was amended by this same slice for lock ordering. ADR-020 now carries it: the statement, the rejected alternative (counting `hand` rows first is check-then-act across two statements, which only narrows the window and pays a round trip to do it), why the session row rather than the `hand` table (the deal must write the column anyway, and one contended row keeps the lock order a tree), and the cost — `HandAlreadyDealtException` acquires a second origin that the constraint-name translation table in ADR-023 structurally cannot cover, because this one is not a constraint violation. ADR-020's "declares exactly two writes" is also corrected; there are five

- **Liquibase had never run.** `liquibase-core` was on the classpath and `spring.liquibase.*` was configured, but Spring Boot 4 moved `LiquibaseAutoConfiguration` into a separate `spring-boot-liquibase` module that was never added. Every migration property was inert. Nothing failed, because an unread changelog and an empty one are indistinguishable until the first migration exists — which is exactly when this surfaced
- **The master changelog matched no files.** `includeAll` used an absolute `classpath:` path that silently resolved to zero changesets; it now resolves relative to the changelog file and is filtered to `.xml`, so the `.gitkeep` placeholder that previously sat in `changes/` cannot crash startup once the directory is genuinely read
- **Documentation named an uninstallable prerequisite.** `SETUP.md`, `docs/devops/local-development.md` and `.opencode/rules/performance-testing.md` all instructed the reader to install or launch Docker Desktop, which needs administrator rights this project does not have and a paid licence above an organisation-size threshold. All three now describe Colima (ADR-016)
- **The two Compose files shared one project namespace.** Both derived their project name from the directory, so each stack reported the other's containers as orphans and `docker compose down --remove-orphans` on either would have destroyed the other. They are now named `eop-app` and `eop-monitoring` explicitly
- **`.env.example` pointed k6 at a container hostname.** `INFLUXDB_URL` was `http://influxdb:8086`, which cannot resolve from the host where k6 runs, and omitted the `/k6` database path
- **The ADR index claimed four delivered decisions were unimplemented.** The OpenAPI contract, the RFC 9457 handler and the first Liquibase changeset all shipped with the card catalogue, and the index still read "No" for each; the front-end row read "No" since July. `docs/adr/README.md` now matches what is on disk
- **The attribution footer disclaimed the content it now has to attribute.** It read "The cards shown above are placeholders written for this project, not Microsoft's" — true for the six invented prompts, and false the moment the real deck was seeded. An attribution notice that denies authorship of the work it credits is worse than none
- **`docs/performance/TRENDS.md` held placeholder rows.** Every cell had been an em dash since the file was created, because the load test had never run against a container. It now carries measured figures and records the baseline reset
- **Configuration consented to an unauthenticated SQL console.** `application.yml` had said `spring.h2.console.enabled: true` since the Walking Skeleton, on the profile every local run uses. The H2 console is arbitrary SQL against the application's own database and accepts a caller-supplied JDBC URL — the CVE-2021-42392 shape — and there is no Spring Security dependency in this project that could have stood in front of it. It was never actually served: exactly as with Liquibase above, Spring Boot 4 moved the autoconfiguration into a separate module, `spring-boot-h2console`, that nothing here depends on, so no class ever read the property. That makes it a latent exposure rather than a live one — one transitive dependency and it arrives with the configuration already saying yes and no review to catch it. The property is now an explicit `false` with the reasoning attached rather than deleted, so whoever adds the module has to change a line that explains why it is off; `application-prod.yml` keeps its own redundant `false` as a second independent guard; and `H2ConsoleAbsentIntegrationTest` carries a tripwire on the autoconfiguration class so the build fails the day the module lands. The documentation that promised a console at `/h2-console` in a `dev` profile — a profile that has never existed either — is withdrawn in `docs/devops/local-development.md` and amended in ADR-008
- **The rule files taught two profiles that have never existed.** `.opencode/rules/configuration.md` stated the convention as `dev` (local), `test` (CI) and `prod` (production); only `prod` is real, alongside the unnamed default. `src/main/resources/` holds `application.yml` and `application-prod.yml` and nothing else, and the test suite activates no profile at all — it overrides the default through `src/test/resources/application.properties`. `.opencode/rules/caching.md` told the reader to disable caching in the `dev` profile and `.opencode/rules/feature-flags.md` to override flags with an `application-test.yml`; neither instruction could be carried out. These files are injected into every agent's context on every session, which makes them the most-read prose in the repository and the likeliest origin of the false consequence withdrawn from ADR-008 above — the fix there corrected the document that repeated the error, this one corrects the documents that generate it. The convention now names the two real profiles and says why it is two and not three, citing ADR-012, so the correction survives being read without the ADR to hand
- **The feature-flag rule prescribed a naming convention no flag has ever used.** It required `ff_{feature}_v{n}` under an `eop.feature-flags.*` root; the one flag that exists is `eop.features.session-lifecycle`, matching ADR-013. No code, configuration, test or ADR ever depended on the fictional form, so the rule has been rewritten to follow the shipped code rather than the code retrofitted to the rule. It had propagated to one other place that still carried it — the story template in `.opencode/agents/product-owner.md`, which named `ff_feature_name_v1` in its flag strategy and in both Gherkin scenarios, so every story written from it would have carried a flag name the rule now bans; that template is corrected here too. It also directed the reader to catalogue flags in `docs/feature-flags.md`, a file that does not exist — flags are recorded in `application.yml` beside their defaults and in ADR-013, and the rule now says so
- **The ADR index disagreed with two of the ADRs it indexes.** ADR-002 had been amended on 2026-07-27 and ADR-012 on 2026-08-10; the index showed the first as plainly `Accepted` and the second as `Accepted (amended)` with no date. An undated amendment reads as current, and a missing one reads as unamended, so the index was quietly overstating how settled two decisions were. Both rows now carry the substance and the date. Because the index has drifted twice for the same reason — keeping it in step is step 5 of a manual checklist — `AdrIndexConsistencyTest` now fails the build when an ADR has no index row, a row links to a missing file, an ADR does not carry exactly one `**Status:**` line to compare against, a status word disagrees, or a dated amendment reaches the index without its date. The invariants are deliberately narrow: a test strict enough to dictate wording would be worked around rather than obeyed
- **`X-Forwarded-For` was believed from any caller, so the join-code throttle could be bypassed by rotating one header.** The application read the last entry of the header and used it as the client address — the key the join-attempt limiter counts failures against. The reasoning was that Caddy is the only published entry point (ADR-017) and Caddy appends to the header, so the last entry is the one the proxy wrote: sound, but valid only if the peer really is the proxy, and nothing checked that. Reached directly — by `./mvnw spring-boot:run` on port 8080, from a sibling container on the Compose network, or through any later change that publishes the application port — a caller supplied its own rate-limiter key, and a fresh value per request meant a fresh empty bucket per request, so the ten-failures-per-address limit never fired. The per-code counter could not compensate, because a code-guessing attacker uses a different code every time. ADR-019 designates that limiter a *primary* security control rather than defence in depth — a six-character join code is thirty bits, unguessable only while guessing is slow — so this was not a thinned-out layer but the removal of the control the entropy budget was calculated against (EOP-26, ADR-021)
- **Trust in a forwarding header is now an explicit, default-denied allow-list.** `eop.web.trusted-proxies` holds literal addresses or canonical CIDR blocks; the header is ignored entirely unless the peer address is on that list, and the default is empty, so an application deployed without a thought about forwarding headers trusts nobody and keys on the peer. A malformed or non-canonical entry fails startup rather than being skipped — silently masking `10.0.0.5/8` to `10.0.0.0/8` would trust sixteen million hosts where the author plainly meant one. Every resolved address is canonicalised before it becomes a map key, because two spellings of one address are two buckets, which is the same defect arriving by another route. `server.forward-headers-strategy` is pinned to `none` in both profiles so neither Tomcat's `RemoteIpValve` nor Spring's `ForwardedHeaderFilter` can launder the header into `getRemoteAddr()` behind the check: their default trust lists cover `172.16.0.0/12`, which contains this project's own Compose subnet. The deployed value sits beside the proxy's pinned container address in `compose.app.yml`, so the two halves of one fact cannot drift apart (EOP-26, ADR-021)
- **A green build had been evidence that the bug was still present.** The integration suite's `freshAddress()` helper gave each test its own throttle bucket by setting `X-Forwarded-For` — a test choosing its own rate-limiter key from outside the process, which is precisely the attack. The suite had been getting its isolation *from the vulnerability*, so closing the hole broke sixteen previously-passing tests. Trusting `127.0.0.1` suite-wide would have let all sixteen pass unchanged and was rejected: it would have re-opened the hole everywhere in the suite except in the tests that assert it is closed. The helper is now `unusedAddressHint()`, documented as having no effect, and the throttling tests get a fresh limiter from `@DirtiesContext` instead of from a forged header (EOP-26, ADR-021)

### Known issues

- **k6 results never reach InfluxDB, so the Grafana dashboard is empty.** Three independent causes: the sample environment pointed at a container hostname (fixed here); direnv exports `.env` at directory entry so an already-running shell keeps the stale value; and InfluxDB has HTTP authentication enabled while the k6 output URL carries no credentials — a direct write with the configured admin credentials returns `401`. k6 logs one write error per flush interval but **exits 0**, so thresholds still gate correctly and nothing checking the exit code ever noticed. The JSON and summary files written to `docs/performance/history/` are the real evidence. Repair needs its own story
